# Bot 协作层设计（多 Agent 团队）

状态：设计稿（未实现）。
范围：在 kova 现有 subagent 运行时之上补齐多 Agent 协作层——Bot 间互发消息、用户↔多 Bot 群聊接力、后台助手、团队花名册。单 Bot 的身份增强（条目化记忆/人格 CAS/习惯）见 `custom-agent-memory.md`；确定性编排见 `workflow-engine-gap.md`（另行立项）；父→子委派与续聊见 `subagent-conversation.md`。

## 结论（先读）

1. **一个 Bot = 一条长驻委派**：subagent YAML 定义（名字/角色/工具面/模型）+ 永不裁剪的委派存档 + private 记忆命名空间。Bot 之间对等，由**调度器**统一驱动。
2. **subagent 运行时覆盖执行层约 80%**（委派持久化 / resume / steer / 审批链 / 并发上限，见 `subagent-conversation.md` V1）。真正要补的只有三块：**Bot 间互发的调度器、群聊接力器、房间/花名册资产**。
3. **五件安全与可靠性设计是一等要求**：协议标记中和（防提示注入）、免费交接（交接块零额外模型回合）、hop 收敛、`OUTCOME_UNKNOWN` 永不重试、进行中回合周期落盘。
4. 分期：T0 直聊互发 → T1 群聊接力 → T2 后台助手/用量 → T3 房间 UI / IM 出口。

---

## 1. 定位与形态

- **Bot**：有名字、角色指令、显式工具面、模型与思考档位、private 记忆的对等 Agent。用户与 Bot 私聊（`bot:<id>`），多个 Bot 与用户同处一个房间（`group:<id>`）。
- **调度器**：sidecar 内的常驻模块（`bots/`），持有房间与各 Bot 的 delegationId，负责消息入队、回合驱动、接力治理、结果回流。所有写花名册的操作只在调度器侧实现——**Bot 之间不直接持有彼此，也不能改其他 Bot 的定义与记忆**（身份完整性硬边界）。
- **不做**：确定性多步编排（模型驱动的协作 ≠ 工作流引擎）；实时镜像面板；iOS/云设备。

## 2. 机制设计规范

以下常量为**起步值**（实现时可调，但语义必须保留）。

### 2.1 回合驱动与投递状态机

每聊天（`bot:<id>` / `group:<id>`）一个串行队列：

- **成批**：新用户消息并入未开跑的批次（≤20 条 / 60K 字符，按 seq 排序）；同一聊天同时只有一个批次在跑，且等待该聊天的助手回合/重试/定时回合全部落定后才开跑。
- **投递状态机**（逐消息持久化，单次原子写）：`pending → processing → delivered / failed / cancelled`，外加三个特殊态：
  - `uncertain`——回合可能已执行：**永不自动重放**；后续追问需显式 ack（`continuationAcknowledged`）；
  - `held`——存在未决回合/问卷时新输入挂起；resume **只重发从未开跑的消息**；
  - `adjusting`——插话中断的过渡态：先落盘，再 abort 在跑回合，未受理的旧输入合并进新批次（一次中断确认覆盖后续连续插话）。
- **重试**：回合在执行任何工具**之前**失败才自动重试，退避 `[8s, 20s]`；`auth / quota / context_too_long / blocked / invalid_request` 不可重试；`AGENT_OUTCOME_UNKNOWN` 永不重试（回合可能已执行，重发=重复动作，包括重复发消息/付款类外部副作用）。
- **崩溃恢复**：跑动中的回合每 **2 秒**把已知状态写入账本——重启后任何状态不得只存在于内存。

### 2.2 群聊接力

**点名解析**：成员按名字长度降序匹配 `@名字`；`@` 前是拉丁式词字符（`mail@alice`）不算点名，前是中日韩字符（`请@某人`）不算吞掉（用 `\p{Script_Extensions}` 区分）；`@` 后紧跟词字符不算（`Alicex` ≠ `Alice`）。

**初始队列**：@到的成员依次入场；无人被 @ 时按群 `replyMode`——`admin`（仅管理员答）或 `all`（管理员先答、其余成员跟上）。

**接力循环**（每房间同一时刻最多一条链）：

```
while (队列非空 && 未取消) {
  若 hops ≥ maxHops > 0 → 收敛（清空队列，跳出）
  bot = 队列.shift()；重读房间花名册（成员可能中途变化）
  交接块随提示词走（免费，见 2.3）；hops++
  result = 跑该 Bot 的回合（kind: 'group'）
  被取消 → unshift 回队首
  safeToContinue=false → 断（等问卷/审批）
  回复是 [PASS] → 该消息标记 pass，continue
  出错 → 房间继续；队列空且管理员 ≠ 出错者 → 管理员顶上
  回复文本 → 记为本跳结论 + 进纪要素材
  回复里 @ 的成员追加进队列（去重、排除自己）
  到限且回复还在 @ 人 → 收敛
  无进展检测：签名 = [botId, 回复, 点名]；无工具进展的精确重复交接 → 房间暂停（no_progress）；
  有工具调用 → 清空签名集
}
收敛 → 让最后一跳的 Bot 收尾（收敛标记 + "总结"提示词），收尾进纪要
纪要落盘（从已产出的文本写，零额外回合）；暂停 → 房间贴系统提示
```

- **hop 上限**：`group.maxHops`，0=不限制（基线），坏值按无限制处理（手改文件不能把群静音），硬顶 20；**上限是宿主侧配置，模型不能改**。
- **上下文窗口**：群上下文取最近 30 条、单条截 4000 字；每个成员只注入与自己相关的窗口 + 纪要，不全员全量。

### 2.3 防护：免费交接与标记中和

- **免费交接**：上一跳的结论随下一跳的提示词走（`<kova-bot-handover>` 块）。来源优先级：房间纪要（结构化结论，复用零成本）> 上一条回复**尾部** 400 字（结论在结尾）；上限 600 字。零额外模型回合、零工具调用。
- **收敛**：到限时不叫下一个，给刚发言的 Bot 发收敛标记 + 总结提示。
- **协议标记中和**：Bot 产出文本里的 `<kova-bot-*>` 标记**和宿主系统提示词自身的块标记**（实现时盘点本仓清单）一律剥除——否则一个 Bot 能在下一个 Bot 的提示词里伪造"宿主通知"。匹配前做 unicode 折叠：零宽字符/组合符剔除、全角 ASCII 折半角、形似连字符归一，记录 origin 映射回原文位置——**只删标记，正文一字不动**。房间简介等用户可写字段过同一道中和。
- **群纪要**：`<kova-bot-group-summary>` 块，最多 6 条 / 总 1200 字 / 单条 240 字；每轮接力结束从本轮已产出的话滚动提炼（零额外回合）；在交接块与成员上下文窗口复用。

### 2.4 后台助手

`bot_start_helper` 把重活放进**独立委派**跑，Bot 本轮立即结束；报告（截 8000 字）作为新输入回流发起聊天。并发与槽位：全局同时跑 **2** 个（与聊天回合**共享**并发预算，且至少留 1 个槽位给回复），每 Bot 排队+运行 ≤ **4**。

### 2.5 记忆

三层 scope：`self`（Bot 自己）/ `team`（团队共享）/ `room`（房间工作状态，即纪要）。限额：单条 1200 字、1000 条、总量 10 万字；topic 子文件；注入按预算选择；写入前脱敏（密钥/证件号拒收——与 `custom-agent-memory.md` §3 同一套正则纪律）。

### 2.6 定时

Bot 归属的定时任务 = automation 的 `ScheduledTask` 增加可选 `agentId` 与 `lastOutcome: "posted" | "quiet" | "failed"`（即 `custom-agent-memory.md` P2 的 habits，直接复用其设计，不另起存储）。种类：`daily / interval / once`；触发即在对应 Bot 的私聊注入任务。

### 2.7 数据与持久化

```
~/.kova/agents/rooms/<roomId>/
├── room.json      # 成员+collabRole、replyMode、maxHops、纪要、计数器
└── transcript.jsonl  # 行式、原子 rename、meta 行、截尾护栏（对齐 subagent 活动文件纪律）
```

不动 state.db；`PI_AGENTS_DIR` 同纪律可用环境变量覆盖（测试走临时目录）。面板聊天记录与委派活动文件沿用现有存储。

## 3. kova 落地

### 3.1 原语对照（机制 → 现状 → 差距）

| 本设计机制 | kova 现状 | 差距 |
| --- | --- | --- |
| 回合驱动（文本进、回合出） | subagent `Task` 启动 + `SendMessage`（running→steer / ended→resume，V1 已实现） | 无本质差距 |
| Bot 持久身份 | 委派活动文件 + 历史存档 + resume；private 记忆 | resume 注入历史上限 100 条/约 2MB——长程记忆靠 private 记忆 + 纪要 |
| 权限审批 | subagentToolGate 与主会话同一套 + 沙箱 | 现状占优，直接复用 |
| 并发槽位 | 每父会话并发上限（默认 8，可配） | 助手槽位规则按 2.4 收紧 |
| 21 式工具面 | 工具组条件注册机制现成（`memory.ts:745-758` 双闸模式） | 新增工具组定义 |
| rooms/state 资产 | 无（委派记录挂父会话） | 新资产（小） |
| 群聊接力器 | 无 | 新代码（核心工作量） |
| relay 防护纯函数 | 无 | 移植实现（见 2.3） |
| Bot 归属定时 | automation（croner/tasks.json/runHistory） | 复用，加 agentId（= habits） |

### 3.2 模型近似与其代价

**Bot = 长驻 delegation**，四个语义差别要接受或补偿：

1. **能力面**：协作层 Bot 应显式声明工具面而非默认全开——团队内天然最小权限，这是相对"全会话 Bot"的**改进**；
2. **对等性**：委派有 ownerSession，Bot 间对等由调度器充当中立总控实现，Bot 之间不直接持有彼此；
3. **持久性**：resume 上下文有上限——长程记忆放 private 记忆（事实条目）+ 房间纪要（工作状态），会话历史只是短期上下文；
4. **渲染**：委派视图在「面板 → 子智能体」tab；团队房间视图为 T3 新增（复用面板对话页组件）。

### 3.3 三缺口的补法

1. **调度器（sidecar 新模块 `bots/`）**：持有 rooms 与各 Bot 的 delegationId，对每个 Bot 都能 SendMessage。宿主侧驱动形态推荐：**automation 运行器同级的常驻服务**（群聊接力需要跨用户消息自主推进；automation 的单实例锁/并发闸纪律直接沿用）；
2. **relay 防护移植**：纯函数模块（hop/免费交接/收敛/标记中和），保持「引擎决定何时、guard 只说什么」的结构——规则表驱动单测不需要真模型；
3. **房间资产**：见 2.7；投递状态机照 2.1 全量实现（`uncertain/held/adjusting` 三态 + 插话合并），这是可靠性的核心，不是可选项。

### 3.4 工具面与权限

注册进 Bot 委派的工具组（门控 = subagent 能力五维 + 新增 `collabRole: chief | admin | member` YAML 字段）：

- 成员可用：`bot_list_team / bot_rooms / bot_message {to, text} / bot_post_group {roomId, text}（**仅单聊发起**，群内禁用——堵递归投递）/ bot_room_history / bot_start_helper / bot_helpers`；
- chief/admin 才可用：`bot_create_group / bot_invite / bot_remove / bot_set_reply_mode / bot_set_max_hops`；
- 硬边界：所有写花名册的操作只在调度器侧实现，Bot 只能通过消息请求变更。

### 3.5 协议与 UI

- protocol 增 `list_rooms / create_room / post_to_room / resume_held / set_room_paused / room_events`（推送沿用 pushActivity 通道）；
- desktop：房间=侧栏「团队」分组，房间视图复用面板对话页组件（消息块带 Bot 头像/名字/PASS/系统提示样式）；手机端只读+发消息；
- IM 出口：`docs/im-channels.md` 通道可绑房间——IM 里 @Bot 的消息进房间，天然对齐点名模型（T3 可选）。

### 3.6 分期与验收

| 期 | 内容 | 验收 |
| --- | --- | --- |
| **T0** | 调度器 + rooms 资产 + 直聊互发（受理回执→steer/resume→结果回流）+ 投递状态机 + hop/预算护栏 | 两个 Bot 互发完成一次往返；kill sidecar 后 uncertain 不重放、held 可手动续；预算打满被拒 |
| **T1** | 群聊接力：@点名（CJK 边界）、replyMode、PASS、错误兜底、hop 收敛、免费交接、无进展暂停、群纪要 | 三 Bot 房间：点名顺序正确；A 失败 B 顶上；maxHops=2 时第三跳收敛收尾；互客气触发 no_progress 暂停 |
| **T2** | 后台助手（槽位 2/4）+ usage 用量流水 | 助手报告回流发起聊天；并发不超槽位 |
| **T3** | desktop 房间视图 + 手机端只读 + IM 出口（可选） | 视觉验收 + IM @消息进房间 |

### 3.7 风险与对策

1. **群聊风暴**：hop 收敛 + 无进展暂停 + 每房间单链串行——三者缺一不可；
2. **转交环**：互发 hop 计数（>4 拒绝）+ 每日每会话预算；
3. **上下文膨胀**：窗口 30 条/单条 4000 字 + 纪要滚动；
4. **审批归属**：委派审批沿 subagentToolGate 挂 ownerSession；房间内发起的助手审批投回房间；
5. **提示注入**：标记中和 + 宿主块标记清单 + 用户可写字段同中和；
6. **调度器单点**：进程内单例（automation 单实例锁纪律），崩溃靠投递状态机 + 委派存档恢复，不引入新存储。

### 3.8 测试策略

- 防护纯函数表驱动：@边界四种、hop 三态、交接两种来源、PASS、无进展签名；
- 投递状态机表驱动：uncertain 不重放 / held 只重发未开跑 / 插话合并；
- 调度器用 fake agent 客户端（规则测试不需要真模型）；
- 回归红线：未加入团队的会话与委派，系统提示词与工具表**字节级不变**（对齐现有缓存纪律测试）。
