Kova 企业服务端（控制面）设计

控制面是客户端契约的源头。服务端优先：客户端 enterprise_* 命令由本契约反向推导。技术栈 Java，背压（Backpressure）为一等设计约束。

Java 21 LTS Spring Boot 3 + WebFlux 背压为核心 PostgreSQL + Redis Kafka 削峰 仅设计，不改代码

1

定位与范围

服务端 = 控制面，承载所有「企业意志」：身份、席位、License、模型网关、技能注册、知识代理、审计与计量、管理台。

服务端（控制面，权威）                客户端（企业模式，消费方）
──────────────────────────            ──────────────────────────
席位 / 角色 / 配额 ─── entitlement ─→ 能力门禁（model.scope / knowledge.scope / skills.allow）
模型网关 + 虚拟密钥 ── 配置下发 ────→ custom_providers（base_url / api_key）
telemetry ingest  ←── 批量上报 ─────  enterprise_telemetry_emit
席位变更 ───────── WS 推送 ───────→  热更新能力集

原则：权威在服务端。客户端只做消费契约 + 本地降级，不自行定义能力边界。

边界：不做客户端 UI；不做模型推理本体（内网 GPU 集群由 vLLM / Ollama 承担）；不做自建 RAG 检索引擎（P3b 可选模块替换）。

2

技术选型

层选型理由
语言 / 运行时Java 21（LTS） + Virtual Threads长期支持、生态成熟；虚拟线程让阻塞调用（JDBC / IdP）也能高并发，配信号量做背压
主框架Spring Boot 3.x + WebFlux（Project Reactor）原生 Reactive Streams，request(n) 即背压原语
备选框架Vert.x更轻、更贴近事件循环；适合纯网关进程
主库PostgreSQL 16 + R2DBC关系模型适合席位/授权；响应式驱动不阻塞事件循环
缓存 / 计数Redis（原子 Lua）配额与限流的低延迟计数，避免 DB 热点
计量削峰Kafka / Pulsar（可选）上报洪峰与聚合解耦，本身即天然背压缓冲
对象存储S3 兼容（MinIO）技能包 / 离线 bundle / 制品
管理台独立 SPA，服务端静态托管管理面与数据面隔离
交付Docker 镜像 + Helm与总览 §7 部署形态对齐

为什么 Java + 响应式：企业流量特征不是「高 QPS」，而是多客户端 + 突发批量上报 + 长连接推送 + 流式推理——全是背压问题。WebFlux 把背压做进框架（request(n)），而非业务补丁。

3

背压设计（核心）

3.1 为什么必须显式做背压

场景无背压的后果
telemetry 批量上报洪峰打满线程/内存 → OOM；或阻塞主库 → 控制面整体不可用
模型网关流式转发慢客户端导致服务端缓冲无限增长 → 内存爆炸
WS 控制通道推送客户端消费慢 → 出站队列无界 → 单连接拖垮进程
配额计数Redis/DB 计数成为热点 → 延迟抖动，反压到网关

3.2 四类背压场景与策略

#场景背压机制溢出策略
B1telemetry 批量上报credit-based pull + 有界队列 + 水位阈值水位超限返回 429 + Retry-After；客户端本地缓冲继续累积
B2模型网关流式转发Flux<DataBuffer> + request(n) 逐块拉取 + limitRate客户端断开即向上游 cancel()；上游慢则反压上游（不本地无界缓冲）
B3WS 控制通道推送每连接有界出站队列 + onBackpressureBuffer(limit, onOverflow)合并丢弃旧值（能力集类幂等），标记 coalesced
B4配额计数Redis 原子计数 + 本地预聚合 + 热点键分片默认 fail-closed（拒绝），可配 fail-open（放行并记账）

3.3 端到端流控链路

图 1 · telemetry 上报的端到端背压：credit 拉取 → 限流 → 有界水位 → 429 反压 → 客户端退避
模型网关链路：
客户端 ◄──request(n)── 网关 ◄──request(n)── 上游 / 内网集群
        （慢客户端只影响本连接，不拖垮进程）

3.4 机制清单（Java / WebFlux 语境）

机制用法
Reactive Streams request(n)背压原语：消费者按需拉取，生产者不超发
limitRate(n) / onBackpressureBuffer(limit, onOverflow)控制批大小与缓冲上界
有界队列 + 水位（low/high watermark）明确「何时开始拒 / 何时恢复」
令牌桶 / 漏桶限流按席位档与用户维度限流
429 + Retry-After标准背压反馈，配合客户端指数退避
Resilience4j（RateLimiter / Bulkhead / CircuitBreaker）舱壁隔离与熔断，防单租户拖垮全局
Java 21 虚拟线程 + Semaphore阻塞调用（JDBC / OIDC / LDAP）的并发上限即背压
连接池上限（R2DBC / Reactor Netty）池满即排队，天然反压上游
Kafka / Pulsar 消费者拉取计量削峰：生产端快则队列增长，消费端按能力拉取
gRPC FlowControl（若走 gRPC）流控窗口，适合内部服务间

3.5 阈值与参数（可配，示意）

参数默认（示意）说明
ingest 并发上限每租户 32舱壁隔离，防单客户打满
ingest 有界队列10k 条 / 32 MB超限即 429
WS 每连接出站缓冲256 条超限合并丢弃旧值
WS 推送合并窗口500 ms能力集变更合并
客户端上报 credit512 条 / 次拉式上报批大小
配额计数窗口日 / 分钟双窗日配额 + 每分钟速率
限流（受限席位）标准席位 1/5按席位档缩放
熔断阈值错误率 50% / 10s打开后快速失败

五个 API 面

图 2 · 服务端组件视图：管理台注入面 ①；客户端用面 ②④；网关面 ③；集成面 ⑤

4.1 面 ① 管理台 REST（仅管理员）

/admin/seats · /admin/seats/{id}（PATCH/DELETE）· /admin/seats/{id}/transfer · /admin/quota · /admin/policy · /admin/license · /admin/reports/usage · /admin/audit

4.2 面 ② 客户端 API

/auth/oidc/callback · /auth/device/enroll · /auth/token/refresh · /entitlement · /catalog/models|skills|knowledge · /telemetry/credit · /telemetry/batch（幂等 eid，可 429）· /usage/me

4.3 面 ③ 模型网关（OpenAI 兼容）

/v1/models · /v1/chat/completions（流式/非流式，虚拟密钥鉴权，同步计量 + 硬配额，request(n) 背压转发）· /v1/embeddings

网关是路径 A 的权威计量点：调用完成即写计量，配额超限直接 429（见总览 §6.1）。

4.4 面 ④ 控制通道 WS

WS /control 推送 entitlement_changed / session_revoked / models_updated / skills_updated / license_notice / quota_notice。复用客户端 remote.ts 的 token/撤销/踢线模式，服务端为其收端；推送有界 + 合并。

4.5 面 ⑤ 集成 API（服务账号）

/oauth/token（Client Credentials）· 与面 ③ 同入口按服务标签计量与限流 · /knowledge/query。

数据模型

org            (id, name, edition, created_at)
team           (id, org_id, parent_id, name)
user           (id, org_id, external_id, idp_subject, status)
seat           (id, org_id, user_id, tier /*admin|standard|restricted|api*/, role_id,
                state /*active|frozen|revoked|transferred*/, issued_at, revoked_at)
entitlement    (id, seat_id, revision, capability_json, quota_json, updated_at)
license        (id, org_id, edition, seat_limits_json, expiry, signature, imported_at)
device         (id, seat_id, fingerprint, enrolled_at, last_seen, state)
credential     (id, owner_id /*user|service*/, kind, secret_ref, rotated_at, revoked)
skill          (id, scope /*enterprise|team*/, team_id, version, signature, acl_json, enabled_forced)
knowledge      (id, scope, team_id, kind /*mcp|rag*/, endpoint, acl_json)
provider       (id, org_id, base_url, api, allow_models_json)
telemetry      (eid PRIMARY KEY, ts, kind, org_id, user_id, team_id, seat_tier,
                session_id, model, input, output, cache_read, cache_write, tokens,
                cost, result, latency_ms, src /*gateway|client|server*/)
audit          (id, ts, org_id, actor, action, target, meta_json)
quota_counter  (date, scope /*user|team|org*/, ref_id, dimension, used, limit)
  • telemetry.eid 唯一：幂等 upsert，天然去重（重试 / 补报安全）。
  • 分区：telemetry 按月分区 + (org_id, ts) / (user_id, ts) 索引，支撑按用户下钻。
  • 配额计数：Redis 原子计数为准，PG 存窗口快照便于对账与报表。
  • 客户端 enterprise_telemetry 表字段是本表子集（总览 §8.3）。
6

关键流程

6.1 IdP 登录与会话换发

客户端 → /auth/oidc/callback（IdP 授权码）
      → 校验 IdP 断言、解析 subject/组
      → 匹配 user + seat（无席位 → 拒绝 / 默认受限席位）
      → 设备入网校验（device.limit）
      → 签发 access（短）+ refresh（存客户端钥匙串）
      → 返回 entitlement（含 revision）

6.2 席位变更 → 能力集版本化推送

管理台改席位/配额/策略
  → entitlement.revision += 1
  → WS /control 推送 entitlement_changed（有界 + 合并）
  → 客户端热更新；断连客户端下次拉取按 revision 对账

6.3 telemetry 上报（幂等 + 背压）

GET  /telemetry/credit  → 按水位下发 credit（或 429 + Retry-After）
POST /telemetry/batch   → 限流 → 有界队列 → Kafka → 聚合写 PG（eid upsert）
429                     → 客户端指数退避，本地缓冲继续累积（不丢、不静默）

6.4 License 席位校验（在线 + 离线）

在线：发放前校验 已用席位 + 1 ≤ seat_limits[tier] 且未过期，超发拒发。离线（空气隔离）：license 为服务端签名凭证，本服务端即校验方，信任根随离线包提供；导入 .lic 即续期。客户端不校验 License。

6.5 模型调用

1) 虚拟密钥鉴权 → user/seat/service
2) Redis 原子预扣配额（日窗 + 分钟窗）；超限 429
3) 路由：路径 A 上游 provider / 路径 B 内网集群
4) 流式转发（request(n) 背压，见 §3.2 B2）
5) 完成计数：input/output/cache tokens → telemetry（src = gateway）
6) 审计：调用级事件（可选抽样）

8

部署与非功能

伸缩

API（①②③⑤）无状态水平扩；WS 有状态需共享状态（Redis pub/sub 或 Sticky + 路由）；计量消费者按 org_id 分区。

可观测性

队列水位、429 比例、WS 积压、网关 P99、配额拒率；OpenTelemetry 贯穿；上报成功率与 lossy 计数自身作为指标。

安全

mTLS / TLS + 令牌、管理员双因子；密钥只存 secret_ref（Vault/KMS）；全表 org_id + 可选 RLS；审计独立留存；国密可选套件。

8.1 性能目标（示意，待压测）

指标目标
网关非流式 P99（不含上游推理）< 200 ms
网关首字延迟（流式，与上游差值）< 50 ms
telemetry ingest 吞吐（单实例批量）≥ 20k 事件/秒
ingest 429 比例（稳态）< 0.1%
WS 推送延迟P99 < 1 s
席位变更生效（在线端）< 2 s

10

风险与开放问题

10.1 风险

风险影响缓解
响应式编程门槛学习成本、误用阻塞调用阻塞调用统一走虚拟线程 + 信号量舱壁；评审强制
WS 有状态与水平扩冲突推送漏达Redis pub/sub 广播 + 客户端 revision 对账兜底
背压策略选错（fail-open vs fail-closed）成本失控 / 可用性下降策略可配；配额默认 fail-closed，计数类可 fail-open
计量洪峰集中于断连恢复ingest 打满credit 拉式 + 429 退避 + Kafka 削峰
单租户内多团队数据隔离越权风险全表 org_id + RLS，查询强制带 scope
Java 服务端与 Bun/TS 客户端栈割裂契约漂移以 OpenAPI/proto 冻结契约，双端生成校验

10.2 开放问题（待确认）

  1. 网关上游协议：只做 OpenAI 兼容，还是兼容 Anthropic 等多家？
  2. telemetry 走 HTTP 批量，还是复用控制通道 WS 连接？（影响背压实现位置）
  3. Kafka 是否必装（小客户内网成本）？还是先用库内队列 + 单机 PG？
  4. 配额计数默认 fail-open / fail-closed 由谁定（客户可配？）。
  5. WS 控制通道是否与客户端 remote.ts 网关复用同端口与鉴权模型？
  6. 管理台与 API 是否分进程（隔离管理面）？
  7. 国密套件是可选插件还是基线（影响密钥与 TLS 实现）。
  8. 是否引入 gRPC（内部服务间）以利用其流控窗口。
