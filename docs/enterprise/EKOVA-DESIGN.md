## 1. 概述与目标

### 1.1 背景

Kova 目前是**单机、单人、单档位**的桌面 AI 助手：Electron 壳（渲染层沿用 Next 静态导出）+ sidecar 里的 pi-agent 本体，所有状态落在本机 `~/Library/Application Support/com.kova.assistant`。项目要继续往前走，目标形态是**企业私有化部署**：

- 企业统一管控登录账号，登录后由企业下发模型，客户端**本地调用**；
- 企业知识库、团队知识库共享；
- 企业 Skill、团队 Skill 共享；
- 整体可交付到客户内网闭环运行（含本地 GPU 模型集群），空气隔离场景可用。

### 1.2 目标

| 编号 | 目标 | 说明 |
|---|---|---|
| G1 | 统一身份 | 复用企业已有 IdP（OIDC / LDAP / 飞书·钉钉），企业发号、企业回收 |
| G2 | 模型管控下发 | 企业统一下发模型与凭据，客户端本地调用；支持内网 GPU 集群（空气隔离） |
| G3 | 知识可控共享 | 企业库 / 团队库分层可见；先接企业已有检索（MCP），后续可选自建 RAG |
| G4 | 技能可控共享 | 企业 Skill / 团队 Skill 注册、签名、下发；管理员可强制启停 |
| G5 | 席位化授权 | 以「席位」作为授权与计量单位，分层售卖 / 分层发放 |
| G6 | 可私有化交付 | docker-compose + Helm；离线 License；信创与等保合规路径 |
| G7 | 单应用双档案 | 同一 Kova 应用新增「企业模式」，与个人档案数据隔离 |

### 1.3 设计原则

1. **控制面 / 数据面分离**：控制面（身份、授权、配额、审计、下发）集中在企业服务端；数据面（推理、会话、文件读写）尽量留在客户端与内网模型集群。
2. **本地优先 + 优雅降级**：断连或服务端不可达时，客户端按最近一次有效授权继续本地工作，仅受席位硬限制；恢复后自动对账。
3. **档案隔离**：企业模式与个人模式使用**独立 appId / 独立数据目录 / 独立密钥环**，互不读写。
4. **协议只增不改**：沿用 `packages/pi-protocol` 的「只增不改、schema loose」铁律，企业能力以 `enterprise_*` 命令与事件增量叠加，不破坏既有 85 条 Tauri 命令。
5. **不过度设计**：P0 只做最小可用闭环（身份 + 席位门禁 + 审计），RAG、信创等按需分期。

### 1.4 已确认关键决策

| 决策点 | 结论 |
|---|---|
| 部署边界 | **完整私有化**：客户内网闭环，含本地 GPU 模型集群 |
| 身份来源 | **复用企业已有 IdP**（OIDC / LDAP / 飞书·钉钉），不自建账号体系 |
| 知识库 | **先 MCP 接企业已有检索系统**，后续可选自建 RAG |
| 客户端 | **同一 Kova 应用新增「企业模式」**，与个人档案隔离 |
| 席位体系 | **分层席位** = 管理员 / 标准 / 受限 / 集成(API) |
| 输出格式 | Markdown 源文档 + 单文件 HTML 阅读版 |

## 2. 现状与差距

### 2.1 现状盘点

| 能力 | 代码位置 | 现状 |
|---|---|---|
| 数据目录 | `apps/electron/main/paths.ts` | 三段式：`KOVA_DATA_DIR` 覆盖 / dev / 正式 `com.kova.assistant`；目录含 `state.db`、`sessions/`、`task-workspace/` |
| 数据库 | `apps/electron/main/db.ts`、`store.ts`、`data.ts` | node:sqlite 优先、better-sqlite3 兜底；`state.db` WAL；表：`sessions / credentials / secrets / custom_providers / models / usage_daily / usage_scan` |
| 密钥落盘 | `apps/electron/main/secret.ts` | **明文直通**（`encrypt` 返回原值）；历史 `enc:v1:` 密文判为缺失 |
| 模型配置 | `data.ts` 的 `custom_providers` + `models` | 已支持自定义 `base_url` / `api` / `headers` → **模型下发≈配置层近乎免费** |
| 技能发现 | `apps/sidecar/pi-agent/src/skills/discovery.ts`、`state.ts` | 分层：工作区 > 生态·工作区 > 系统 > 生态·用户 > 插件；启用态存 SQLite kv |
| 插件 | `apps/sidecar/pi-agent/src/plugins/plugins.ts`、`plugins/marketplace.json` | 本地市场，仅本地源 |
| 知识源 | `apps/sidecar/pi-agent/src/subagent/knowledge.ts` | 只有 `files`（glob 关键词扫描）与 `mcp`（网关调用）两类；**纯内存扫描、无 embedding / 向量 RAG（设计如此）** |
| 协议 | `packages/pi-protocol/src/index.ts` | 「只增不改；schema loose」；queue / stamp / transcript / notifications / interactions / errors / payloads / validate |
| IPC | `apps/electron/preload/index.ts`、`main/ipc.ts`、`main/registry.ts` | `window.kovaHost { invoke, eventsOn, channelsOn }`；主进程注册中心已移植 85 条命令 |
| 会话存储 | sidecar `storage/storage.ts`、`main` `hostdb.ts` | 每会话 `<id>.jsonl`；hostdb 双模（host SQLite RPC / bun:sqlite 测试） |
| 服务端雏形 | `main/remote.ts`、`main/update.ts`、`main/backup.ts`、`main/tunnel.ts` | 已有 node:http+ws 网关（配对码 / token / `REMOTE_DENIED`）、R2 更新检查、PIABK 备份（S3 SigV4 / WebDAV）、隧道 |
| 用量统计 | `data.ts` 表 `usage_daily` / `usage_scan` | 已有按**会话 × 日期**的 token 用量（`input/output/cache_read/cache_write/tokens/messages/by_model`）和扫描水印；**仅本地、按会话粒度、无用户归属、无上报通道** |

### 2.2 差距清单（本设计要解决的）

| 差距 | 影响 | 严重度 |
|---|---|---|
| **完全无身份 / 无认证概念** | 无法做企业管控的根基 | 阻断 |
| **密钥明文落盘**（`secret.ts`） | 企业凭证（模型 Key、KB Token）不可这样存 | 高 |
| 无多用户 / 无档案隔离 | 一人多岗、企业/个人混用会串数据 | 高 |
| 技能 / 插件仅本地 | 无法企业共享、无法管理员强制 | 高 |
| 无 RAG 能力 | 企业知识库检索质量受限（本期以 MCP 兜底） | 中 |
| 无配额 / 计量下发 | 席位售卖与成本治理缺依据 | 中 |
| **无按用户计量 / 无埋点上报** | 现有 `usage_daily` 只按会话统计、无用户归属、无上报通道；无法回答「哪个用户/团队/席位用了多少 token」 | 高 |
| 无审计 | 等保 / 内控不达标 | 中 |

### 2.3 可复用资产（重要）

- **模型下发**：`custom_providers` + `models` 已支持自定义 `base_url`，企业只需下发「虚拟密钥 + 网关地址」即可，客户端改动极小。
- **传输与网关**：`remote.ts` 已有 HTTP + WebSocket 同端口、配对码、token、消息类型白名单（`REMOTE_DENIED_TYPES`）、撤销踢线，可作为**企业控制通道**的技术底座。
- **更新 / 备份**：`update.ts`（R2 `latest.json` + 12h 节流）与 `backup.ts`（PIABK 信封 + S3/WebDAV）可复刻为**企业配置/技能包下发**与**企业备份**通道。
- **协议增量**：`pi-protocol` 的 loose schema 让新增 `enterprise_*` 类型零破坏。
- **技能分层**：`discovery.ts` 的层叠 + 同名前层遮蔽机制，天然适合插入「企业层 / 团队层」。
- **计量底座**：`usage_daily` / `usage_scan` 已有 token 计数字段与扫描水印，企业计量**只需在其上加「用户归属」维度**并把本地聚合结果上报，不必另造统计引擎。

## 3. 总体架构

### 3.1 控制面 / 数据面

```
┌──────────────────────── 客户内网（空气隔离可选） ────────────────────────┐
│                                                                          │
│  ┌── 控制面（企业服务端，Kova Enterprise Server） ──────────────────┐    │
│  │  IdP 连接器  │ 席位/授权中心 │ 模型网关 │ 技能注册中心 │ 审计中心 │    │
│  │  License 校验 │ 配额与计量   │ KB 代理  │ 下发/对账     │ 管理台   │    │
│  └───────▲──────────────▲───────────────▲──────────────▲───────────┘    │
│          │  mTLS/HTTPS   │               │              │                │
│          │  控制通道(WS)  │               │              │                │
│  ┌───────┴──────────────┴───────────────┴──────────────┴───────────┐    │
│  │                     客户端（Kova 桌面 · 企业模式）                 │    │
│  │   身份会话 · 席位能力解析 · 本地会话/文件（数据面）                │    │
│  └───────▲───────────────────────────▲──────────────────────────────┘    │
│          │ 推理请求                    │ 检索请求                          │
│  ┌───────┴───────────┐    ┌───────────┴───────────┐   ┌───────────────┐  │
│  │ 本地 GPU 模型集群  │    │ 企业现有检索系统(MCP)  │   │ 企业/团队 KB   │  │
│  │ (vLLM/Ollama)      │    │ / 自建 RAG(可选)       │   │ 对象存储/DB    │  │
│  └───────────────────┘    └───────────────────────┘   └───────────────┘  │
└──────────────────────────────────────────────────────────────────────────┘
```

- **控制面**：授权、下发、审计、配额；所有「企业意志」都在这里。
- **数据面**：会话内容、文件、推理流量；尽量不经过控制面（隐私 + 延迟）。

### 3.2 组件职责

| 组件 | 职责 | 部署位置 |
|---|---|---|
| IdP 连接器 | 对接 OIDC / LDAP / 飞书·钉钉，换发企业会话 | 服务端 |
| 席位/授权中心 | 席位发放、角色映射、能力解析、撤销 | 服务端 |
| 模型网关 | 虚拟密钥、路由、配额、审计、允许清单 | 服务端 |
| 内网模型集群 | vLLM / Ollama 承载开源模型 | 客户内网 GPU |
| 技能注册中心 | 上传、签名、版本、可见范围、强制启停 | 服务端 |
| KB 代理 | MCP 代理转发；可选自建 RAG | 服务端 |
| 审计中心 | 登录、席位变更、模型调用、技能启用、导出 | 服务端 |
| 管理台 | 席位发放/回收、配额、策略、审计查询 | 服务端（Web） |
| 客户端企业模式 | 身份会话、能力门禁、本地执行、降级 | 客户端 |

### 3.3 档案隔离（个人 vs 企业）

| 维度 | 个人档案 | 企业档案 |
|---|---|---|
| appId | `com.kova.assistant`（现状） | 新增 `com.kova.assistant.enterprise` |
| 数据目录 | 复用现状 | 独立目录（`KOVA_DATA_DIR` 派生或独立 userData） |
| 密钥环 | 系统钥匙串现有条目 | 独立命名空间 |
| 会话/技能/插件 | 现状 | 独立，互不读取 |
| 协议 | 现状命令 | 现状命令 + `enterprise_*`（企业模式下才注册） |

> 复用 `paths.ts` 的三段式机制，只需扩展「档案」维度即可，不改动既有目录约定。

## 4. 席位体系（核心）

### 4.1 四档席位定义

| 席位 | 定位 | 典型对象 | 一句话 |
|---|---|---|---|
| **管理员 Administrator** | 企业治理者 | IT 管理员、安全负责人 | 管人、管模型、管技能、看审计，不做日常重业务 |
| **标准 Standard** | 主力生产力 | 研发、产品、设计、职能 | 全量企业/团队知识与技能，独立配额 |
| **受限 Restricted** | 受控使用者 | 外包、实习生、试点、临时岗 | 能力显式收窄：可见范围小、配额低、限制外发 |
| **集成 API** | 系统对接 | 服务账号、CI、上游平台 | 无界面，纯 API/批处理，服务级限流与审计 |

### 4.2 席位权益矩阵

图例：● 全量　◐ 受限　○ 无　✎ 可管理（而非仅使用）

| 能力维度 | 管理员 | 标准 | 受限 | 集成 API |
|---|---|---|---|---|
| 客户端形态 | 桌面 + 管理台 | 桌面 | 桌面 | **无 UI**（服务账号） |
| 席位数量 | 1~少量 | 大多数 | 按需 | 按集成数 |
| 模型可见范围 | ● 全部 + ✎ 配置 | ◐ 策略允许集合 | ○ 仅「受限集合」 | ● 策略允许集合 |
| 模型配额 | 高（含管理开销） | 独立配额 | **低配额 + 速率上限** | 服务级配额与并发上限 |
| 企业知识库 | ● + ✎ 授权 | ● 按部门/团队范围 | ○ 或 ◐ 白名单文档 | ● 按服务范围 |
| 团队知识库 | ● + ✎ | ● 本团队 | ◐ 只读子集 | ● 指定团队 |
| 自建 RAG（后期） | ✎ 建库/切分/重排 | ◐ 使用 | ○ | ◐ 调用 |
| 企业 Skill | ● + ✎ 强制启停 | ● 可用 | ◐ 白名单 | ● 白名单 |
| 团队 Skill | ● + ✎ | ● 可用 | ◐ 白名单 | ● 白名单 |
| 个人 Skill / 插件 | ● | ●（企业策略可禁） | ◐ 仅本地、禁外发 | ○（无 UI） |
| 自定义模型/Provider | ✎ 策略级 | ◐ 策略允许下 | ○ | ○ |
| 外部网络出口 | ✎ | ◐ 策略 | **○（默认禁）** | ◐ 策略 |
| 文件/内容导出 | ● + 审计 | ●（水印/审计可选） | **◐ 受限（可禁导出）** | ◐ API 出口 |
| 审计可见性 | **✎ 全量查询** | ○ 仅自己 | ○ | ○（自身调用可查） |
| 用量计量与报表 | **✎ 全量下钻**（用户/团队/模型/席位） | ◐ 仅见自己用量 | ◐ 仅见自己用量 | ◐ 按服务标签聚合 |
| 用量上报 | ● 服务端直采 + 客户端上报 | ● 客户端埋点上报 | ● 客户端埋点上报 | ● 服务端直采（无客户端） |
| 设备绑定额度 | 多设备 | 1~N（策略） | 1 | 服务实例 |
| 管理台访问 | ● | ○ | ○ | ○ |
| 席位转移 | ✎ 执行 | — | — | — |

> 矩阵是**策略默认值**，可由管理员在企业策略里对「标准/受限」做进一步收窄（例如把某部门的受限席位知识范围再限一层）。

### 4.3 「席位」与「角色」的关系

- **席位 = 授权容量与权益档**：决定「能用多少、能看到多大范围、有没有管理权」，是**售卖/发放单位**，也是 License 计量单位。
- **角色 = 职责边界**：映射 IdP 组，决定「在席位上具体是哪个部门/团队、属于哪个知识范围」。
- 二者正交组合：

```
最终能力 = 席位档位（天花板） ∩ 角色策略（可见范围/团队） ∩ 企业策略（全局开关）
```

例：标准席位 + 「研发一部」角色 → 有标准权益，但知识与团队 Skill 只对研发一部可见。

### 4.4 席位生命周期

| 阶段 | 触发 | 动作 | 客户端表现 |
|---|---|---|---|
| **发放** | 管理员在管理台建席位 / IdP 组同步 | 生成席位记录，绑定用户/角色/配额；更新 License 已用计数 | 登录后拉取能力集，即时生效 |
| **变更** | 调整档位 / 加角色 / 调配额 | 版本号 +1；控制通道推送 `enterprise_entitlement_changed` | 热更新能力集，无重启 |
| **冻结** | 试用到期 / 风控 / 离职待办 | 保留席位但禁用登录 | 下次心跳被拒，转受限降级页 |
| **回收** | 离职 / 合同结束 | 释放席位、撤销令牌、下发生效；**释放后席位可转移** | 会话失效，企业数据不可再访问 |
| **转移** | 回收后重新分配 | 席位 ID 复用，审计记录「A→B」 | 新持有人正常登录 |
| **续期** | License 续签 | 更新 License 有效期 | 到期前提示，到期后按策略降级/停用 |

**离线 License 席位校验（空气隔离场景）**：

- License 为**服务端签名**的结构化凭证：`{ org, edition, seatTiers{admin,standard,restricted,api}, expiry, limits, machineBinding? }`。
- 服务端启动时校验签名 + 有效期 + 席位用量 ≤ 授权数量；**超发直接拒发新席位**。
- 客户端不做 License 校验（信任服务端），避免多端密钥。
- 续期 = 导入新的 `.lic` 文件；到期后按策略：只读降级 / 全停。
- 签名算法与信任根在交付时随离线安装包一并提供（与 §7.3 同源）。

### 4.5 客户端按席位降级（能力门禁）

客户端不硬编码席位，而是消费服务端返回的**能力集（entitlement）**：

```jsonc
// enterprise_entitlement（示意，schema loose）
{
  "seat": "standard",
  "capabilities": {
    "model.scope":       ["gpt-oss-120b", "qwen3-32b"],   // 允许的模型
    "knowledge.scope":   ["kb://team/rd-frontend"],        // 可见知识源
    "skills.allow":      ["enterprise/*", "team/rd-frontend/*"],
    "export.enabled":    true,
    "egress.enabled":    false,                            // 外网出口
    "device.limit":      2
  },
  "quota": { "tokensDaily": 500000, "ratePerMin": 60 },
  "revision": 17,
  "expiresAt": "2026-12-31T23:59:59Z"
}
```

降级规则（断连 / 过期 / 席位不足）：

1. **在线**：以服务端最新能力集为准；本地缓存作兜底。
2. **断连未过期**：沿用缓存能力集继续本地工作（本地优先），仅硬限制生效（如配额耗尽）。
3. **过期 / 撤销**：转「受限降级」——只读已有会话、禁新建外部调用；提示重新登录。
4. **席位档位变化**（如标准→受限）：热更新 UI（隐藏不可用入口），不删除已有本地数据。

### 4.6 席位与计量

- **计量单位**：席位（授权）+ Token/day（用量）+ 并发（API 席位）。
- 席位决定「计量口径与可见范围」：管理员看全量报表，标准/受限只看自己，集成 API 按服务标签。
- 实现细节（埋点点、事件 schema、上报管道、聚合报表）见 **§6 计量与埋点体系**；本节仅定义席位侧的授权/配额语义。

## 5. 能力域（按席位展开）

### 5.1 身份与准入

```
登录：客户端 → 打开系统浏览器/内嵌页 → IdP(OIDC 授权码 / LDAP 绑定 / 飞书·钉钉扫码)
      → 回调换取企业会话 → 拉取席位能力集 + 短期令牌 → 入网
设备：首次登录需「设备入网」（设备指纹 + 席位 device.limit 校验），管理员可踢设备
令牌：短期 access token + 可刷新 refresh；存系统钥匙串（替换 secret.ts 明文口径）
撤销：管理员撤销 → 控制通道推送 → 客户端立即失效会话
```

| 席位差异 | 管理员 | 标准 | 受限 | 集成 API |
|---|---|---|---|---|
| 登录方式 | IdP + 管理台账号 | IdP | IdP | 服务账号密钥（Client Credentials） |
| 设备数 | 多 | 策略（默认 2） | 1 | 服务实例（不适用） |
| 会话时长 | 长 | 标准 | **短（更频繁复验）** | Token 短 + 密钥轮换 |
| 撤销响应 | — | 即时 | 即时 | 即时（含密钥吊销） |

### 5.2 模型供给

**两条供给路径并存**：

- **路径 A · 企业模型网关**（在线为主）：客户端配置「虚拟密钥 + 网关 base_url」→ 走现有 `custom_providers`；网关做鉴权、路由到上游或内网集群、配额与审计。**客户端改动最小**。
- **路径 B · 内网 GPU 集群**（空气隔离）：vLLM / Ollama 直接暴露 OpenAI 兼容端点，客户端同样以 `custom_providers` 接入；模型清单由企业下发。

| 席位差异 | 管理员 | 标准 | 受限 | 集成 API |
|---|---|---|---|---|
| 可见模型 | 全部 | 策略集合 | 受限集合（小/低成本） | 策略集合 |
| 配额 | 高 | 独立 | 低 + 速率上限 | 服务级并发 |
| 可否自定义 Provider | 策略级 ✎ | 策略允许下 ◐ | ○ | ○ |
| 审计粒度 | 全量 | 调用级 | 调用级 | 调用级 + 服务标签 |

### 5.3 知识库

**分期**：

1. **P3a（先做）**：以 **MCP 代理**接企业已有检索系统。客户端沿用现有 `knowledge.ts` 的 `mcp` 源类型——「命名一个 MCP 服务器与工具，agent 走作用域化网关自行调用」。企业只需把检索系统封装为 MCP 端点。
2. **P3b（后做，可选）**：自建 RAG（embedding + 向量库）作为**实现替换**，不改 schema 与上层调用（与现设计「向量 RAG 本期不做，将来是模块实现替换」的约定一致）。
3. **权限在查询时判定（服务端）**：不把全库同步到客户端；按席位 + 角色在**检索时**裁剪结果（服务端 ACL），避免本地越权。

| 席位差异 | 管理员 | 标准 | 受限 | 集成 API |
|---|---|---|---|---|
| 企业 KB | ● + ✎ 授权 | ● 部门/团队范围 | 白名单文档 | 服务范围 |
| 团队 KB | ● + ✎ | ● 本团队 | 只读子集 | 指定团队 |
| 建库/切分/重排 | ✎ | ○ | ○ | ○ |
| 检索审计 | ● | ◐ | ◐ | ● |

### 5.4 技能与插件

在现有**五层发现**（工作区 > 生态·工作区 > 系统 > 生态·用户 > 插件）基础上，插入**企业层 / 团队层**，形成七层；同名前层遮蔽规则不变。

```
工作区 > 生态·工作区 > 团队(企业下发) > 企业(企业下发) > 系统 > 生态·用户 > 插件
```

- **注册中心**：上传 → 签名（内容哈希 + 企业签名）→ 版本 → 可见范围（企业/团队/部门）→ 下发。
- **管理员强制启停**：企业/团队层技能由**管理员策略**决定启用态，**覆盖用户 kv**（`state.ts` 现有 kv 判定之上新增一层「策略优先」）。
- **离线签名包**：空气隔离场景以签名 bundle 形式随安装包/离线介质下发，客户端校验签名后加载。
- **受限席位**：仅白名单技能可用，个人技能/插件按策略可禁。

| 席位差异 | 管理员 | 标准 | 受限 | 集成 API |
|---|---|---|---|---|
| 企业/团队 Skill | ● + ✎ 强制 | ● | ◐ 白名单 | ● 白名单 |
| 个人 Skill | ● | ●（策略可禁） | ◐ 仅本地 | ○ |
| 发布权限 | ✎ 上传/签名/授权 | ○ | ○ | ○ |

### 5.5 集成 API 席位（无 UI）

- 形态：**服务账号**（Client Credentials），无桌面 UI，纯 API/批处理。
- 能力：模型调用、KB 检索、企业 Skill 调用（白名单），带**服务级限流与审计标签**。
- 复用现有 `remote.ts` 网关的鉴权/路由骨架（配对码换成服务密钥），或独立轻量 API 端点。
- 典型场景：CI 流水线代码评审、上游平台批处理、问答机器人后端。

## 6. 计量与埋点体系

> 需求源头：企业要能回答「**每个用户用了多少 token**」——按用户、团队、模型、席位下钻，并以此做配额与成本治理。现有 `usage_daily` / `usage_scan` 只是**本地、按会话**的计数，必须补上**用户归属 + 埋点上报 + 集中聚合**。

### 6.1 两条计量线（关键设计）

> 一句话：**权威计量必须落在流量路径上**。客户端埋点解决「可见性」，解决不了「可信」。

| | 路径 A · 企业模型网关 | 路径 B · 空气隔离直连内网 GPU |
|---|---|---|
| 流量路径 | 客户端 → 网关 → 上游/集群 | 客户端 → 内网 vLLM/Ollama |
| 服务端可见性 | ● 全量可见 | **○ 网关不在路径上 → 服务端看不到** |
| 权威计量 | **网关同步计量**（可信、可硬控） | 服务端无数据 |
| 硬配额执行 | 网关实时判定并拒绝（如 429） | 需**集群前置计量代理**才能硬控 |
| 客户端埋点用途 | 本人可见性 + 断连对账 | 唯一数据来源，但**不可信**：仅适合成本可见性，不可用于计费/硬配额 |

**结论**：
- **异步统计**（报表、成本可见性）可走客户端埋点上报，容忍延迟。
- **同步硬配额**（计费、限流）必须由**网关或集群前置代理**在路径上实时执行。
- 路径 B 优先方案：在 GPU 集群前架**轻量计量代理**（OpenAI 兼容入口 + 计量 + 配额），客户端配置指向代理；若客户拒绝代理，则明确告知「硬配额不可用」。

### 6.2 埋点点清单

| 埋点点 | 触发时机 | 关键字段 | 权威来源 |
|---|---|---|---|
| `model.call` | 每次 LLM 调用完成 | provider、model、input/output/cacheRead/cacheWrite tokens、latencyMs、result、会话、席位、用户、团队 | 网关（A）／客户端（B） |
| `model.stream.end` | 流式结束 | 同 `model.call` + 首字延迟 | 同上 |
| `kb.query` | 每次知识检索 | 来源 ID、scope、命中数、耗时、席位 | 服务端代理／客户端 |
| `skill.invoke` | 每次 Skill 调用 | skill id、scope、版本、result | 客户端 |
| `auth.login` / `device.enroll` | 登录 / 设备入网 | 用户、席位、设备指纹、IP、result | 服务端（权威） |
| `seat.change` / `policy.change` | 席位/策略变更 | 操作者、目标、前后值 | 服务端（权威） |
| `export` | 内容导出（审计强相关） | 类型、目标、字节数 | 客户端 + 服务端 |
| `quota.exceeded` | 触达硬配额 | 用户、维度、当前值/上限 | 网关／代理（权威） |

> 原则：埋点点覆盖**计量**与**审计**两类；审计事件（登录、导出、席位变更）由服务端权威产生，计量事件两条路径各有权威来源。

### 6.3 事件 schema（统一）

```jsonc
// enterprise_telemetry 事件（schema loose，只增不改）
{
  "eid": "01H...",                 // 幂等键，客户端生成 UUIDv7
  "ts":  "2026-10-14T12:00:00Z",
  "org": "acme",
  "kind": "usage.model.call",       // 命名空间：usage.* / audit.*
  "user": "u_123", "team": "rd-frontend", "seat": "standard",
  "session": "s_abc", "device": "d_9f",
  "model": "qwen3-32b", "provider": "gw-1",
  "usage": { "input": 1200, "output": 300, "cacheRead": 0, "cacheWrite": 0, "tokens": 1500 },
  "cost": 0.012,
  "result": "ok", "latencyMs": 840,
  "src": "gateway"                  // gateway | client | server
}
// 只采计量与元数据，**绝不采 prompt/response 正文**
```

### 6.4 上报管道

```
埋点产生（客户端/网关）
  → 本地 SQLite 缓冲队列表 enterprise_telemetry（离线可用）
  → 批量打包（分批 + gzip）
  → 控制通道 / HTTP 上报（指数退避重试、断连对账）
  → 服务端入库（按 eid 幂等 upsert）
  → 聚合：用户 / 团队 / 模型 / 席位档 / 部门 / 时间
  → 管理台报表（管理员下钻；标准/受限仅见自己）
```

| 机制 | 设计 |
|---|---|
| 本地落账 | 先写 `usage_daily`（会话 × 日期，字段复用现状）+ 新增**用户归属**（`profile_id` / `user_id` / `team_id`） |
| 上报粒度 | 以 `usage_daily` 聚合行累加上报；幂等键 `(org, user, session, date, model)` |
| 重试 | 指数退避 + 最大重试；失败计入缓冲 |
| 缓冲上限 | 按条数 + 字节双上限；超限丢最旧并记录 `lossy` 计数（**不撑爆磁盘，不静默丢**） |
| 断连对账 | 恢复后按 `usage_scan` 水印增量补报，服务端 upsert 去重 |
| 顺序 | 允许乱序；服务端按 `date` 归集，不依赖到达顺序 |

### 6.5 服务端聚合与报表

- **维度**：用户 / 团队 / 部门 / 模型 / 席位档 / 时间（日、周、月）。
- **报表**：Top N 用户与团队、按模型 token 分布、席位配额消耗率、异常突增/越权告警。
- **权限**：复用 §4.2 席位规则——管理员**全量下钻**；标准/受限只见自己；集成 API 按服务标签聚合。

### 6.6 审计与计量合并为单一通道

- 原草案的 `enterprise_audit_emit` 与计量埋点**合并为同一个上报机制** `enterprise_telemetry`，用 `kind` 前缀区分（`audit.*` / `usage.*`），避免两套通道、两套缓冲、两套重试。
- 本地缓冲表统一为 `enterprise_telemetry`；服务端可再按 `kind` 分流入审计库 / 计量库。

### 6.7 隐私与合规

- **只采计量与元数据，不采内容正文**（prompt / response 一律不入埋点）。
- 保留周期可配（默认 180 天）；支持按用户/时间导出与删除。
- 审计事件（登录、导出、席位变更）按等保要求**单独设置留存策略**（可长于计量）。

## 7. 私有化部署形态

### 7.1 编排

| 形态 | 适用 | 组成 |
|---|---|---|
| **docker-compose** | 中小客户 / 试点 | 控制面服务 + 网关 + 管理台 + （可选）向量库 + （可选）模型集群接入 |

- **离线安装包**：镜像 tar + Helm chart + License `.lic` + 企业根证书 + 技能签名 bundle。
- **空气隔离**：全部介质离线带入；客户端企业模式预置内网地址（不可改外网）。
- **升级**：沿用 `update.ts` 的清单模式（`latest.json` + 节流），企业侧改为**内网制品库**。

### 7.3 合规

| 项 | 措施 |
|---|---|
| 等保三级 | 审计全留存、最小权限、传输加密、账号可追溯、双因子（管理员） |

| 计量留存 | 只采元数据不采正文（见 §6.7）；审计与计量分流留存 |

## 9. 分期路线与验收

| 期 | 主题 | 交付 | 验收标准 |
|---|---|---|---|
| **P0** | 安全基线 + 身份骨架 + 埋点底座 | 档案隔离、钥匙串企业密钥、IdP 登录、设备入网、席位模型（四档）、能力集解析与门禁；**`enterprise_telemetry` 缓冲表 + 上报通道 + 用量归属列** | 管理员可发放/回收席位；标准/受限/API 三种登录态可分；断连可降级；密钥不再明文；**本地能按用户查到自己 token 用量** |
| **P1** | 模型下发 + 权威计量 | 模型网关（虚拟密钥 + 配额 + 审计 + **同步计量**）、模型清单下发、内网 GPU 集群接入（**前置计量代理**） | 企业下发模型客户端即可用；配额实时生效；**管理台可按用户/团队/模型下钻 token**；空气隔离下走内网集群且计量可用 |
| **P2** | 技能共享 | 注册中心、签名、企业层/团队层发现、管理员强制启停、离线 bundle | 企业/团队技能可下发；管理员强制覆盖用户开关；离线包签名校验通过 |
| **P3** | 知识库 | MCP 代理接企业检索；权限查询时裁剪；（可选）自建 RAG | 标准见团队库、受限只见白名单；越权查询被拒；RAG 为可选加装 |
| **P4** | 私有化交付 | docker-compose + Helm、离线 License、空气隔离安装包、信创与合规材料 | 客户内网一键起；离线席位校验正确；超发被拒；等保/密评材料齐；计量留存策略生效 |

**里程碑依赖**：P1 依赖 P0 的身份、能力集与埋点底座；P2 依赖 P0 的档案与密钥；P3 依赖 P0 的席位 ACL；P4 依赖 P0~P3 全部可离线运行。

**服务端先行**：P0 / P1 的**服务端契约先落地并冻结**（详见 [`EKOVA-SERVER-DESIGN.md`](EKOVA-SERVER-DESIGN.md) §9：S0/S1），客户端按冻结契约实现，避免契约漂移。

## 10. 风险与开放问题

### 10.1 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 协议「只增不改」下的企业扩展可能膨胀 | 维护成本上升 | 企业类型集中命名空间 `enterprise_*`，独立文档与版本 |
| 空气隔离下下发难 | 技能/模型更新滞后 | 离线签名 bundle + 内网制品库 |
| 服务端 ACL 成为单点 | 检索延迟/可用性 | 结果缓存 + 客户端本地兜底 |
| 明文密钥历史包袱 | 迁移成本 | 仅企业档案强制钥匙串，个人档案不强制 |
| 受限席位定义过于粗暴 | 用户体验 | 策略化收窄，而非硬编码 |
| 多租户 vs 单租户 | 复杂度 | 先单客户内网（单租户），多租户留待后续 |
| **路径 B 无网关 → 服务端计量盲区** | 无法权威计量/硬配额 | 集群前置计量代理（首选）；纯直连时声明「仅统计、不硬控」 |
| **客户端上报不可信**（可篡改/漏报） | 只可用于可见性，不可计费 | 计费/硬配额以网关或代理为准；客户端数据仅对账 |
| 埋点缓冲撑爆磁盘 / 静默丢数 | 数据不完整或占满空间 | 双上限 + `lossy` 标记 + 显式提示，不静默丢 |

### 10.2 开放问题（待确认）

1. 管理台形态：独立 Web 管理台，还是复用桌面端「管理员模式」？（倾向独立 Web，隔离管理面）
2. IdP 首选顺序：OIDC / 飞书 / 钉钉 / LDAP 哪个先行？
3. 席位档位是否可再细分（如「标准」再分知识范围档）？
4. 客户端额外交互：企业模式与个人模式如何切换（同一进程双档案 / 独立实例）？
5. License 机器绑定：是否需要（离线单机场景）？绑定粒度（客户 / 集群 / 设备）？
6. 计量上报频率与离线缓冲策略（断连多久、缓冲多大）。
7. 技能签名的信任根由谁签发（Kova 官方 / 客户自签）？
8. 计费口径：按 token 计费还是按席位订阅？（影响是否必须网关权威计量）。
9. 埋点上报路径：走控制通道（WS）还是独立 HTTP 端点？带宽与空气隔离影响。
10. 路径 B 是否强制部署计量代理，还是接受「硬配额不可用」的降级交付？
