Kova 企业私有化版 · 席位体系设计

以「席位」为组织骨架：企业统一管控登录账号、下发模型、共享企业/团队知识与 Skill，并完整交付到客户内网闭环运行（含本地 GPU 模型集群）。含按用户 token 计量与埋点设计。

概述与目标

目标形态是企业私有化部署：企业统一管控登录账号，登录后由企业下发模型、客户端本地调用；企业知识库 / 团队知识库共享；企业 Skill / 团队 Skill 共享；整体交付到客户内网闭环，空气隔离可用。

1.1 目标

编号目标说明
G1统一身份复用企业已有 IdP（OIDC / LDAP / 飞书·钉钉），企业发号、企业回收
G2模型管控下发企业统一下发模型与凭据，客户端本地调用；支持内网 GPU 集群（空气隔离）
G3知识可控共享企业库 / 团队库分层可见；先接企业已有检索（MCP），后续可选自建 RAG
G4技能可控共享企业 Skill / 团队 Skill 注册、签名、下发；管理员可强制启停
G5席位化授权以「席位」作为授权与计量单位，分层售卖 / 分层发放
G6可私有化交付docker-compose + Helm；离线 License；信创与等保合规路径
G7单应用双档案同一 Kova 应用新增「企业模式」，与个人档案数据隔离
G8按用户计量与埋点能回答「每个用户 / 团队 / 模型用了多少 token」，支撑配额与成本治理

1.2 设计原则

控制面 / 数据面分离

身份、授权、配额、审计、下发集中在服务端；推理、会话、文件读写留在客户端与内网集群。

本地优先 + 优雅降级

断连时按最近一次有效授权继续本地工作，恢复后对账；仅席位硬限制生效。

档案隔离

企业模式与个人模式使用独立 appId / 数据目录 / 密钥环，互不读写。

协议只增不改

沿用 pi-protocol 的 loose schema，企业能力以 enterprise_* 增量叠加。

席位体系（核心）

4.1 四档席位

管理员

企业治理者：IT / 安全负责人

  • 管人、管模型、管技能、看审计
  • 配额高（含管理开销）
  • 可访问管理台

标准

主力生产力：研发 / 产品 / 设计 / 职能

  • 全量企业/团队知识与技能
  • 独立配额
  • 仅见自己用量

受限

受控使用者：外包 / 实习生 / 试点

  • 可见范围小、白名单
  • 低配额 + 速率上限
  • 默认禁外网出口

集成 API

系统对接：服务账号 / CI / 上游平台

  • 无 UI，纯 API / 批处理
  • 服务级限流与审计标签
  • 按服务标签计量

4.3 席位与角色的关系

最终能力 = 席位档位（天花板） ∩ 角色策略（可见范围/团队） ∩ 企业策略（全局开关）

席位 = 授权容量与权益档（售卖/发放单位、License 计量单位）；角色 = 职责边界（映射 IdP 组，决定部门/团队/知识范围）。

4.4 席位生命周期

阶段触发动作客户端表现
发放管理台建席位 / IdP 组同步生成席位，绑定用户/角色/配额，更新 License 已用登录后拉取能力集，即时生效
变更调档位 / 加角色 / 调配额版本 +1，推送 enterprise_entitlement_changed热更新能力集
冻结试用到期 / 风控保留席位但禁用登录心跳被拒，转降级页
回收离职 / 合同结束释放席位、撤销令牌会话失效，企业数据不可访问
转移回收后重新分配席位 ID 复用，审计记录 A→B新持有人正常登录
续期License 续签更新有效期到期前提示，到期按策略降级

离线 License 席位校验：服务端签名凭证 { org, edition, seatTiers{admin,standard,restricted,api}, expiry, limits }；启动校验签名 + 有效期 + 用量 ≤ 授权数，超发拒发；客户端不校验 License（信任服务端）；续期 = 导入新 .lic。

4.5 客户端按席位降级

{

  "capabilities": {

    "knowledge.scope": ["kb://team/rd-frontend"],
    "skills.allow":    ["enterprise/*", "team/rd-frontend/*"],

  1. 在线：以服务端最新能力集为准，本地缓存兜底。
  2. 断连未过期：沿用缓存能力集继续本地工作，仅硬限制生效。
  3. 过期 / 撤销：转受限降级——只读已有会话、禁新建外部调用。
  4. 档位变化：热更新 UI，不删除已有本地数据。

能力域（按席位展开）

5.1 身份与准入

登录：客户端 → 系统浏览器/内嵌页 → IdP(OIDC / LDAP / 飞书·钉钉)
      → 回调换取企业会话 → 拉取席位能力集 + 短期令牌 → 入网
设备：首次登录需设备入网（设备指纹 + device.limit 校验），管理员可踢设备
令牌：短期 access + 可刷新 refresh，存系统钥匙串（替换明文口径）
撤销：管理员撤销 → 控制通道推送 → 客户端立即失效会话
席位差异管理员标准受限集成 API
登录方式IdP + 管理台IdPIdPClient Credentials
设备数多默认 21服务实例
会话时长长标准短，复验频繁Token 短 + 轮换

5.2 模型供给

路径 A · 企业模型网关

客户端配置「虚拟密钥 + 网关 base_url」，走现有 custom_providers；网关做鉴权、路由、配额、审计。客户端改动最小。

路径 B · 内网 GPU 集群

vLLM / Ollama 暴露 OpenAI 兼容端点，同样以 custom_providers 接入；空气隔离场景。需前置计量代理才有硬配额。

5.3 知识库

  1. P3a 先做：以 MCP 代理接企业已有检索（复用 knowledge.ts 的 mcp 源）。
  2. P3b 后做（可选）：自建 RAG 作为实现替换，不改 schema 与上层调用。
  3. 权限在查询时判定（服务端）：不全库同步，检索时按席位 + 角色裁剪（服务端 ACL）。

5.4 技能与插件

工作区 > 生态·工作区 > 团队(企业下发) > 企业(企业下发) > 系统 > 生态·用户 > 插件

注册中心：上传 → 签名（内容哈希 + 企业签名）→ 版本 → 可见范围 → 下发。管理员强制启停覆盖用户 kv（在 state.ts 判定之上加「策略优先」层）。空气隔离以签名 bundle 下发。

5.5 集成 API 席位（无 UI）

服务账号（Client Credentials），纯 API / 批处理；能力含模型调用、KB 检索、企业 Skill 白名单，带服务级限流与审计标签。复用 remote.ts 鉴权/路由骨架。典型：CI 代码评审、上游批处理、问答机器人后端。

6

计量与埋点体系

需求源头：企业要能回答「每个用户用了多少 token」——按用户 / 团队 / 模型 / 席位下钻，支撑配额与成本治理。现有 usage_daily 只是本地、按会话的计数，必须补上 用户归属 + 埋点上报 + 集中聚合。

6.1 两条计量线（关键设计）

一句话：权威计量必须落在流量路径上。客户端埋点解决「可见性」，解决不了「可信」。

路径 A · 企业模型网关路径 B · 空气隔离直连内网 GPU
流量路径客户端 → 网关 → 上游/集群客户端 → 内网 vLLM/Ollama
服务端可见性● 全量可见○ 网关不在路径上 → 看不到
权威计量网关同步计量（可信、可硬控）服务端无数据
硬配额执行网关实时判定并拒绝（429）需集群前置计量代理才能硬控
客户端埋点用途本人可见性 + 断连对账唯一来源，但不可信：仅成本可见性

结论：异步统计（报表、成本可见性）可走客户端埋点，容忍延迟；同步硬配额（计费、限流）必须由网关或集群前置代理在路径上实时执行。路径 B 优先在集群前架轻量计量代理（OpenAI 兼容入口 + 计量 + 配额）；客户拒绝代理则明确告知「硬配额不可用」。

6.2 埋点点清单

埋点点触发时机关键字段权威来源
model.call每次 LLM 调用完成provider、model、input/output/cache tokens、latencyMs、result、会话、席位、用户、团队网关（A）／客户端（B）

6.4 上报管道

图 2 · 计量数据流：埋点 → 本地缓冲 → 批量上报 → 幂等入库 → 聚合报表

6.5 服务端聚合与报表

  • 维度：用户 / 团队 / 部门 / 模型 / 席位档 / 时间（日、周、月）。
  • 报表：Top N 用户与团队、按模型 token 分布、席位配额消耗率、异常突增/越权告警。
  • 权限：管理员全量下钻；标准/受限只见自己；集成 API 按服务标签聚合。

6.6 审计与计量合并为单一通道

原草案的 enterprise_audit_emit 与计量埋点合并为同一机制 enterprise_telemetry，用 kind 前缀区分 audit.* / usage.*；缓冲表统一为 enterprise_telemetry，服务端按 kind 分流入审计库 / 计量库。

6.7 隐私与合规

  • 只采计量与元数据，不采内容正文（prompt / response 不入埋点）。
  • 保留周期可配（默认 180 天）；支持按用户/时间导出与删除。
  • 审计事件按等保要求单独留存（可长于计量）。

私有化部署形态

7.1 编排

形态适用组成
docker-compose中小客户 / 试点控制面 + 网关 + 管理台 +（可选）向量库 +（可选）模型集群接入
Helm / K8s大型客户 / 已有 K8sStatefulSet / Deployment，含 HPA、PVC、Secret
单机一体化POC / 演示一个容器内含控制面 + 网关（无 GPU）

7.2 卸载与安装

  • 离线安装包：镜像 tar + Helm chart + License .lic + 企业根证书 + 技能签名 bundle。
  • 空气隔离：介质离线带入；客户端企业模式预置内网地址（不可改外网）。
  • 升级：沿用 update.ts 清单模式（latest.json + 节流），企业侧改为内网制品库。

7.3 合规

项措施
等保三级审计全留存、最小权限、传输加密、账号可追溯、双因子（管理员）
密评国密 SM2/SM3/SM4 可选套件（HTTPS/TLS、签名、落盘）
信创麒麟 / 统信 UOS 客户端；鲲鹏 / 龙芯服务端 arm64 / loongarch 构建
数据出境默认不出内网；外网出口按席位默认关闭（受限强制关）
计量留存只采元数据不采正文（见 §6.7）；审计与计量分流留存

enterprise_knowledge  (id, scope, kind, endpoint, acl_json)
-- 计量与埋点（§6）
enterprise_telemetry  (eid PRIMARY KEY, ts, kind, profile_id, user_id, team_id, seat,
                       session_id, model, input, output, cache_read, cache_write, tokens,
                       cost, result, latency_ms, src, state, retry, meta_json)

用量归属：sessions 增列 profile_id / user_id / team_id（沿用补列范式），使 usage_daily 聚合行带用户维度。缓冲表兼作审计缓冲，不出第二张表。

8.4 复用点

8.5 密钥处置

企业相关密钥（模型虚拟 Key、KB Token、服务账号密钥）必须走系统钥匙串 / safeStorage 并限定档案命名空间；个人档案沿用现状（不强制迁移）。建议新增 enterpriseSecretStore（旁路新增，不动 secret.ts 原函数），仅企业模式启用。

分期路线与验收

期主题交付验收标准
P0安全基线 + 身份骨架 + 埋点底座档案隔离、钥匙串企业密钥、IdP 登录、设备入网、四档席位、能力集门禁；enterprise_telemetry 缓冲表 + 上报通道 + 用量归属列管理员可发放/回收席位；三种登录态可分；断连可降级；密钥不再明文；本地可按用户查 token 用量
P1模型下发 + 权威计量模型网关（虚拟密钥 + 配额 + 审计 + 同步计量）、模型清单下发、内网 GPU 集群接入（前置计量代理）企业下发模型即可用；配额实时生效；管理台可按用户/团队/模型下钻 token；空气隔离下计量可用
P2技能共享注册中心、签名、企业层/团队层发现、管理员强制启停、离线 bundle企业/团队技能可下发；管理员强制覆盖用户开关；离线包签名校验通过
P3知识库MCP 代理接企业检索；权限查询时裁剪；（可选）自建 RAG标准见团队库、受限只见白名单；越权被拒；RAG 为可选加装
P4私有化交付docker-compose + Helm、离线 License、空气隔离安装包、信创与合规材料客户内网一键起；离线席位校验正确；超发被拒；等保/密评材料齐；计量留存策略生效

依赖：P1 依赖 P0 的身份、能力集与埋点底座；P2 依赖 P0 的档案与密钥；P3 依赖 P0 的席位 ACL；P4 依赖 P0~P3 全部可离线运行。

风险与开放问题

10.1 风险

风险影响缓解
协议扩展膨胀维护成本上升集中命名空间 enterprise_*，独立文档与版本
空气隔离下下发难技能/模型更新滞后离线签名 bundle + 内网制品库
服务端 ACL 单点检索延迟/可用性结果缓存 + 客户端本地兜底
明文密钥历史包袱迁移成本仅企业档案强制钥匙串
路径 B 无网关 → 计量盲区无法权威计量/硬配额集群前置计量代理；纯直连声明「仅统计、不硬控」
客户端上报不可信只可可见性、不可计费计费/硬配额以网关或代理为准
埋点缓冲撑爆磁盘 / 静默丢数数据不完整或占空间双上限 + lossy 标记 + 显式提示

10.2 开放问题（待确认）

  1. 管理台形态：独立 Web 管理台，还是复用桌面端「管理员模式」？
  2. IdP 首选顺序：OIDC / 飞书 / 钉钉 / LDAP 哪个先行？
  3. 席位档位是否可再细分（「标准」再分知识范围档）？
  4. 企业模式与个人模式如何切换（同一进程双档案 / 独立实例）？
  5. License 机器绑定是否需要？绑定粒度（客户 / 集群 / 设备）？
  6. 计量上报频率与离线缓冲策略（断连多久、缓冲多大）。
  7. 技能签名的信任根由谁签发（Kova 官方 / 客户自签）？
  8. 计费口径：按 token 计费还是按席位订阅？（决定是否必须网关权威计量）
  9. 埋点上报路径：走控制通道（WS）还是独立 HTTP 端点？
  10. 路径 B 是否强制部署计量代理，还是接受「硬配额不可用」的降级交付？
