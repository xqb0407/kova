# 设计文档:工作流模式 UI(v2)

> 定稿于 2026-10-07。前置:`plans/workflow-mode-design.md`(目标态设计,已按 M1→M3b 实现于
> `workflow-mode-backup` 分支)与 `plans/workflow-mode-audit.md`(自审计,定位四处高危缺陷)。
> 本文档只设计 UI 层:v1 的 UI 是跟着六个 fix 长出来的,本文把它收敛成一份「合并前该长什么样」
> 的目标态——keep/change/fix 三列对着 v1 资产写,不推倒重来。
>
> 审计教训是本文的第一输入。四条高危缺陷全部是 UI 感知的(冻结、丢报告、挂死、假恢复),
> 所以 v2 的设计原则第一条就是:**每个产出面必须声明自己的数据通道与键**,组件不得假设
> 自己活在模型回合内。

## 0. 设计原则(从审计教训推导,每条对应一个已付过的学费)

1. **后台事实源原则**。工作流执行在 sidecar 后台,模型回合结束 ≠ 运行结束。任何工作流 UI
   的数据通道声明为三层:push 通知行(`workflow_state_push`,无 id,Rust 广播,主通道)>
   RPC 全量快照(`get_workflow_state`,挂载/换线程水合)> 低频轮询(仅 running 态 10s,
   对账兜底,不是主通道)。v1 的学费:UI 冻在「运行中 0/7」而 journal 里两步都在跑。
2. **确认即授权**。提案卡是用户授权的唯一时刻:步骤、agent、gate 命令**逐字**、参数槽,
   全部在卡上可见。确认按钮一次语义(见 §4.1)。v1 的学费:「编排工作流」被模型理解成
   自己去干活——因为授权面不明确,模型不确定自己该不该动手。
3. **控制权只在按钮上**。用户消息永远不打断后台运行(运行中收消息 = 正常聊天);暂停/
   继续/清除是仅有的控制面,且都带期望状态护栏。v1 的学费:goal 档「用户消息即接管」
   被错误抄过来,用户发一句「确认」把正在跑的子代理掐了。
4. **状态可对账**。卡片状态行永远显示「N/M 步 · k token · 状态」,能和 journal 快照对上;
   重启恢复后缺失历史结果的步骤明确标注,不假装可用。v1 的学费:readRunFile 零调用点,
   恢复后插值出 `<missing step result>`。
5. **复用既有外壳,不发明新形态**。常驻条 = goal-strip 同壳;步骤详情 = 委派活动视图同件;
   快照心智 = queue-v2 的「全量快照最后胜出」。桌面端的视觉语言沿用 v1 已定的:11px 正文、
   muted 分层、kind 记号(▸ ◈ ▣ ◆)、呼吸点表 running。

## 1. 信息架构:四个面,各管一件事

| 面 | 位置 | 职责 | 数据通道 |
|---|---|---|---|
| A 对话流 | 提案行锚定在触发 user 消息后,原地变运行卡 | 主叙事:提案→确认→执行→终态凭据 | push 行 + 锚点表 |
| B 常驻条 | composer 正上方(goal-strip 同壳) | 状态一览 + 快捷控制,离开十分钟回来一眼可判 | push 行 + 水合 |
| C 剧本库 | 自动化页「工作流」段 | 存/取/带参运行/运行历史 | RPC(list/run/delete) |
| D 步骤详情 | A/B 的步骤行点开 | 单步深查:委派活动流 / 命令门结果 / 评审投票 | 复用委派活动通路 |

四面同源:全部读同一份 run 快照(pi-workflow store),区别只在展开粒度。**禁止第二事实源**
——v1 的教训之一就是轮询、chunk、RPC 三路各自更新 store 时没有统一的「最后胜出」合并点,
v2 在 `pi-workflow.ts` 收敛为单 store 单合并函数(按 updatedAt 取新,步骤态按字段级覆盖)。

## 2. 状态机 → UI 映射

run 状态沿 v1 实际实现的六态(`workflow-strip.tsx` STATUS_CLASS 为准;设计文档里的 blocked
v1 未实现,v2 仍不做,无进展兜底走 failed + 原因行):

| status | 常驻条 | 对话卡 | 卡上按钮 |
|---|---|---|---|
| proposing | 绿呼吸点「正在拟剧本…」 | 提案行 skeleton( shimmer 一行) | — |
| proposed | 琥珀点「剧本待确认」(点开 Popover = 完整提案卡) | 提案卡全量展开 | 确认并开始 / 驳回 |
| running | 绿呼吸点 + `N/M 步 · k token` + 暂停 | 运行卡全量展开 | 暂停 |
| paused | 琥珀点「已暂停 N/M」 | 运行卡(interrupted 步琥珀) | 继续 / 清除 |
| complete | 灰「完成 · k token」 | 终态卡(默认折叠为一行) | 存为剧本 / 清除 |
| failed | 红「失败: <步骤名>」 | 终态卡展开 + 失败步骤红行 + 原因 | 重跑(预留) / 清除 |

关键变化:complete 后对话卡**默认折叠**(v1 全量步骤列表永驻会话,百步 run 刷屏);
报告本体不再长在卡里——终局合成报告以正常 assistant 消息回投(可继续追问),卡退化为
「执行凭据」(一行:结果摘要 + token + 展开箭头)。

## 3. 组件线框

### 3.1 提案确认卡(WorkflowPlanCard v2)

v1 保留:phase 分组、gate 命令逐字 code 块、驳回意见回流、「上一版为什么被退回」虚线条。
v2 新增:**args 参数槽表单**与**步骤详情折叠**。

```
┌──────────────────────────────────────────────────────┐
│ 工作流剧本 · 确认后开始执行                            │
│ ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄ │
│ 上一版为什么被退回:别爬 Twitter,用 RSS 源            │
│                                                       │
│ ▍采集                                                 │
│   ▸ 拉取 BTC/ETH 行情        @Explorer      待跑     │
│   ▸ 拉取市场新闻(RSS)       @Explorer      待跑     │
│ ▍校验与汇总                                           │
│   ◈ 交叉验证行情异常          2 位评审       待跑     │
│   ◆ 汇总日报                  @Explorer      待跑     │
│   ▣ pnpm test && pnpm lint   ⏎ 退出码即判定  待跑    │
│                                                       │
│ 参数  币种 [BTC, ETH____]   时间范围 [24h___]         │
│       (args 声明生成;仅 required 硬拦,可选留空=缺口标记)│
│                                                       │
│ 确认后由执行器自动编排:无依赖步骤并发跑,命令门按     │
│ 退出码判定,全部完成后自动交付报告。                  │
│                                  [驳回]  [确认并开始] │
└──────────────────────────────────────────────────────┘
```

- gate 行:命令在**提案时逐字可见**是授权语义的根,永不允许「确认后再看」。
- 参数槽:v1 的 args 只在剧本库重跑时有表单,提案卡没有——用户第一次确认时看不到参数,
  改参只能靠驳回重拟。v2 把 args 声明直接渲染成卡内表单,值进指纹(§5.3 of 主设计),
  确认的语义从「授权这份步骤清单」升级为「授权这份步骤清单 + 这组参数」。
- 步骤行 hover 出现 `⌄`:展开单步声明(prompt 全文、agent 定义名、依赖、模型覆盖)。
  默认全折叠——提案卡 7 步以上时 v1 的常开形态太长。

### 3.2 运行卡(WorkflowRunCard v2)

```
┌──────────────────────────────────────────────────────┐
│ ▸ 采集日报        运行中 3/7 步 · 12.4k token  ●⏸   │  ← 常驻条 Popover 与对话卡同源
│ ▍采集                             ⏸                  │
│   ▸ 拉取 BTC/ETH 行情      @Explorer   完成    2.1k │
│   ▸ 拉取市场新闻(RSS)     @Explorer   运行中… ●    │  ← 点行 = 步骤详情(面 D)
│ ▍校验与汇总                                           │
│   ◈ 交叉验证行情异常        2 位评审     待跑        │
│   ▣ pnpm test                            待跑        │
│   ◆ 汇总日报                             待跑        │
│   ── foreach「采集」子项:  ●●◐○○ (2/5 完成)        │
└──────────────────────────────────────────────────────┘
```

v2 的三处变化:

1. **步骤行可点开**(v1 是纯文本行,「哪一步在干什么」只有标题级信息)。delegate 步点开
   = 委派活动视图(v1 的 `subagent_activity` 面板组件直接复用,一行新代码不写);gate 步
   = 命令 + 退出码 + stderr 尾部;verify 步 = 投票列表(`real` 徽标 + reason);synthesize
   = 报告全文。详情展开**不换页**,行下原地抽屉。
2. **每行尾加该步 token**(v1 只有 run 级总数)。执行器的 JournalEntry 已有 usage 字段,
   纯展示改动。这是成本可对账的一部分:用户能看出「12.4k 里 8k 烧在卡住的那步」。
3. **interrupted 语义可视化**:恢复运行的卡上,上次中断的步骤行保留琥珀色 + 「已中断,
   将重跑」标记,而不是混进 pending 灰里——用户需要分辨「还没跑到」和「跑了一半被停」。

### 3.3 常驻条(WorkflowStrip v2)

形态不变(goal-strip 同壳,composer 正上方),修的是通道与键:

```
┌──────────────────────────────────────────────────┐
│ ● 采集日报 · 3/7 步 · 12.4k token        [⏸]    │   running
└──────────────────────────────────────────────────┘
```

- v1 保留三态面(proposed → Popover 提案卡 / running → 状态行 / 终态 → 摘要 + 清除)。
- **complete 态可永久清除**(v1 清除后不复活即可);proposed 态的 Popover 卡与对话提案行
  是**同一个组件同一份状态**,确认在任一处生效,另一处随下一次快照同步——v1 已做到,
  保留,但 v2 要求两处的动作都带**各自的 threadId**(见 §4.2)。
- 条上新增一个 v1 没有的东西:**数据新鲜度兜底标记**。push 通道超过 30s 无事件且轮询
  对账发现快照未变、但存在 running 步骤超过步骤 timeoutMs 时,条右侧出琥珀「?」,
  hover 显示「步骤 <名> 已运行超时上限,执行器仍在等待」——把审计缺陷 3(无步骤超时,
  UI 永远「运行中」)在 UI 层显式化,哪怕 sidecar 侧超时修复失效,用户也能看见异常。

### 3.4 剧本库(playbooks-panel v2)

v1 形态保留(ZCode 自动化页同构:卡片直排 + 参数 chips + 最近运行状态),v2 两处增量:

1. **运行历史与对话打通**:历史行记录 runId,点击跳转对应会话并滚动到终态卡
   (锚点表 v1 已有,补一个「按 runId 查锚点」的查询)。跨会话跳转是 M3a 留下的断头路——
   历史看得见、现场回不去。
2. **「已存剧本」徽标回流**:运行卡上点了「存为剧本」后,剧本库对应卡出现「来自运行
   <短id>」来源徽标,与 hostdb 的 source 字段("saved"/"imported"/"builtin")对齐。

### 3.5 步骤详情(面 D,新组件壳)

统一抽屉壳,四类步骤四种内容,全部只读:

```
┌─ 步骤详情 · 拉取市场新闻(RSS) ─────────────────────┐
│ 状态 运行中 · 已 42s / 上限 20min · 1.3k token      │
│ agent Explorer · 模型 glm-5(会话继承)              │
│ ─ 任务 ──────────────────────────────────────────  │
│ (插值后的 prompt 全文,占位符已替换处高亮)          │
│ ─ 活动 ──────────────────────────────────────────  │
│ (delegate:复用委派活动流组件;gate:退出码+stderr;  │
│  verify:投票卡列表;synthesize:报告全文)           │
└─────────────────────────────────────────────────────┘
```

「上限 20min」来自步骤 timeoutMs——把 §3.3 的兜底标记在详情里给出精确数字。

## 4. 交互细节(每条都是 v1 真机事故的对应修法)

### 4.1 确认按钮一次语义

「确认并开始」点击后立即转 `busy + disabled`,文案变「执行器启动中…」,直到下一次
快照返回 running(proposed→running 迁移)或报错回弹。**这不是装饰**:审计 1.3 的启动竞态
(双击确认两 kick 双双穿过同步守卫)在 runner 侧修占位,但 UI 侧的 disabled 是同一防线的
前置闸,两层都要。驳回同理(textarea 提交一次)。

### 4.2 threadId 键纪律(审计 1.5,架构性接缝)

四个动作面各带**自己的** threadId,不假设两边同键:

- 对话提案行:锚点表的 threadId(锚定消息所属线程)
- 常驻条:当前 `mainThreadId`
- 剧本库「运行」:发起 RPC 时的当前线程
- 所有 push 行消费:按 run.threadId 入 store,store 在 `rebindRunThread` 时随
  `migrateWorkflow` 迁移(v1 已挂,保留)

任何一侧出现「有快照但动作无响应」,先查键(`pi-workflow.ts` 保留 v1 加的诊断日志:
创建运行、确认、恢复三个分水岭各一条)。

### 4.3 报告回投与终态卡的出现时机

sidecar 排队重试(5s × 120)已修投递不丢;UI 侧的唯一纪律:**终态卡折叠态在报告消息
实际回投后渲染**,顺序 = 先报告消息后凭据卡。若报告排队期间用户继续聊天,报告插在下一条
user 消息之前(队列语义),卡锚点不动。

### 4.4 恢复运行的「历史结果不可用」标注

瘦身行恢复 + run 文件缺失时(audit 1.1 的退回路径),相关步骤行灰 + tooltip「历史结果
不可用,该步将重跑」;常驻条终态摘要加同款后缀。**不许静默**——v1 的学费就是恢复后
插值 `<missing step result>` 混进 prompt,用户毫无感知。

## 7. v3 修订:列表改编排图(实机反馈 + 一次真实失败驱动)

> 定稿于 2026-10-07 晚,推翻了 §3.1/§3.2 的「phase 分组列表」形态。两个输入:
> ① 用户反馈列表形态「很丑」且看不出依赖关系;② 一次真实失败——质检门没写
> dependsOn,排进第一波,在空工作区上 `test -f …` 退出 1,gate 默认 abort,
> 整轮以「运行失败 0 token」告终。**依赖关系是这个 UI 的第一语义**,列表把它
> 藏在一行 `← scope, market, …` 的尾巴里,图把它变成可见的边。

### 7.1 形态

- 节点 = 步骤,连线 = dependsOn;分层用**最长路径**(纯函数,见
  `lib/pi/workflow-graph.ts`,不引布局库——100 步上限用不上通用解)。
- 节点按状态着色:待跑灰 / 运行中翠绿脉冲 / 完成淡绿 / 失败红底 / 中断琥珀;
  左侧色条按 phase 区分,上方配图例(phase 从「分组标题」降级为「节点的第二属性」)。
- 节点内容:kind 徽标(▸ 方块 / 门 / 复核 / 汇总)、标题、@agent、评审数、
  每步 token、超时「?」、foreach 子项点阵;gate 的命令行在节点内逐字截断展示。
- **无依赖的 gate 挂琥珀「最先执行」徽标**——这次失败的直接成因,提案卡上
  一眼可见(与服务端 `gateDependencyWarnings` 同一条判据的两个出口)。
- 点节点 = 下方展开详情面板(不重复标题;头部只有状态/耗时/token,正文分节
  任务/判定/投票/产出/错误);抽屉详情仍走按需 RPC。
- 终态默认折叠保留;失败时在图下方给一条明确的失败条(失败于「哪一步」+ 原因),
  不再重复 statusLine(v2 里上下两行都是「运行失败」,纯噪声)。

### 7.2 同批修掉的两个真 bug(都不是视觉问题)

1. **中文参数名静默失效**:`{{args.行业}}` 这类占位符在 ASCII-only 的字符集下
   提取不到声明(提案卡没有参数槽可填)、运行时也插不进值(占位符原样漏进
   子代理的 brief)。现在声明提取与运行时插值共用 `ARG_NAME_CHARS`
   (Unicode 字母/数字/`_`/`-`),一处定义两处用。
2. **无依赖的门没有提案期提醒**:服务端在 propose 工具回执里带 warning
   (不阻断——对既有环境做检查的门有正当用法),卡片上同步出「最先执行」徽标。

### 7.3 落点

`lib/pi/workflow-graph.ts`(布局,纯函数 + 单测)、
`components/agent-thread/workflow-graph.tsx`(图组件)、
`workflow-cards.tsx`(卡片改用图 + 抽屉重做)。§5 变更表里 7/8/11 三项的实现
形态随之改变,语义不变。

### 7.4 确认动作上提到常驻条,对话内的卡只做记录

实机反馈:剧本卡在对话里带着「驳回/确认并开始」,输入框上方的常驻条同时有
「确认剧本」——同一件事两个按钮,是两份歧义。拆分按**职责**而不是按位置:

- 对话里的剧本卡 = **记录**:编排图 + 参数名 + 「在输入框上方确认」的去向提示,
  只读(历史回看、审计「我批准的是哪张图」就看它)。
- 常驻条弹层 = **决策**:`WorkflowConfirmPanel`——逐字命令门(授权时刻必须可见)、
  参数槽(必填校验)、驳回带意见、确认开始。弹层宽度放不下编排图,所以图不在这
  重复;「确认的就是这串字面量」这条纪律由命令门列表承担。

运行态不变:暂停/继续/存为剧本仍在对话内的运行卡上(strip 只做提案态的决策面)。

### 7.5 参数不再是准入门槛(实机反馈)

「对话框上方没展开,为啥还一定要输入参数?」——问题在 v2 定的规则本身:
`{{args.x}}` 派生出来的参数**全是可选**(符号只表达「这里会变」),运行时留空时
按既定语义插成显式缺口标记 `<missing arg: x>`,让子代理自己判断(设计文档 §4.3 的
原话:「未提供的参数留显式缺口标记——静默留空会让下游把缺口当事实」)。
前端却把「没有默认值就必须填」当成准入条件,把模型随口写的占位符变成了用户的
必填项,与契约矛盾。改为:

- **硬拦**(确认按钮禁用):声明 `required: true` 且未填、或数字类型填了非数字
  (服务端必拒,前端先一步)。
- **软提示**(放行):可选参数留空——面板上一行说明「不插值,步骤里显示为缺口标记,
  由子代理自行判断;想锁定就填上」。

### 7.6 gate 结构读错不再让用户等六轮(实机第三次同类事故)

现场(转录):同一个 `steps[6] (gate-report) needs gate.command` 被拒 **六次**,
模型每轮都在改命令内容——先怪 `&&`、再怪中文字符、再改用 ASCII 文件名、最后用
`pwd` 做「最小化诊断」——直到第七次才把 `command` 放进嵌套的 `gate` 对象里。
根因是报错只说「needs gate.command」而没说**在哪**(schema 是嵌套的,弱模型读不出)。

两处修复(互补,不互斥):
1. **容忍扁平写法**:`kind:"gate"` 时顶层的 `command`/`args`/`timeoutMs` 归一进
   `gate`(嵌套优先)。能跑就让它跑——把「模型读错 schema」变成用户的等待是最差的
   失败模式。这是本仓一贯的「宽松归一」口径(validatePlan 本来就在做同类收窄)。
2. **报错自解释**:真缺命令时,reason 里直接给出字面形状
   `{"kind":"gate","gate":{"command":"test","args":[...]}}` 并点明「不是步骤顶层字段」。

### 7.7 参数区默认折叠(第三次实机反馈:不强制了,但还杵在那里)

7.5 取消了强制填参,面板上仍摆着三个空输入框——「还是这样的」。参数本身的来路
是对的(模型按提示词约定把「重跑会变的值」写成 `{{args.x}}`,存成剧本后就是参数表),
问题在于**默认展开**把一次性运行当成了需要用户逐项确认的场景。改为:

- 默认折叠一行:`参数(可选 3 个) market、region、competitors ·  留空由子代理自行判断 · 点开可锁定`;
- 点开才出现输入框与「留空 = 缺口标记」说明;
- **硬缺口(必填未填 / 数字类型填错)不受折叠影响**,始终在面板上以红字显示——
  否则会出现「按钮灰着、却看不到为什么」的死局;
- 初始展开条件只有两个:已有值(库路径运行),或存在必填缺口。

### 7.8 「点了继续没反应」:槽位被水合覆盖 + 迁移不推快照(实机)

现场:运行第一次确认后正常开跑(执行器活着),但常驻条/运行卡显示
「已暂停:sidecar restarted while the workflow was running」,用户点 ▶ 得到
`workflow is not resumable: <sessionId>`。两个独立缺陷叠在一起:

1. **`restoreWorkflow` 会覆盖活槽**。它的调用点按「会话(run)在不在内存里」判断,
   而不是按「工作流槽在不在」;run 被驻留驱逐时,一次普通的水合就会拿转录瘦身行
   /全量 run 文件(可能更旧、或正处在写入中间)**覆盖正在跑的槽**,还把 running
   步骤记成 `interrupted`——这正是审计 1.4 预言的混用后果。修法:槽位已存在就
   直接返回,恢复只服务「进程里没有这个槽」这一种情况。
2. **线程键迁移不推快照**。`migrateWorkflow` 把槽从草稿键挪到会话键后不发状态,
   UI 继续捧着迁移前的旧快照(暂停),于是「显示暂停、点继续被拒、其实在跑」。
   修法:迁移后补一次 `emitWorkflowStateFor(newThreadId)`。

顺带把 ▶ 做成**幂等**:槽位缺失先从转录水合(与 `get_workflow_state` 同款两段式);
已在 running 时不报错,重踢一次执行器(runner 内去重)并回当前快照——控制面上的
按钮不该因为「状态其实是对的」而变成报错源。错误文案补上 `status=…` 便于下次排查。

### 7.9 点节点 = 看这一步的实时输出

诉求:「每个节点看不到流输出具体情况,点开能看到」。现成的流在哪:工作流的
`delegate`/`synthesize` 步骤本来就登记委派记录并推活动流(`registerDelegation` +
`onActivity → pushActivity`),「子智能体」面板就是那条流的现成视图(Task 委派同款)。
两处补齐:

1. **sidecar:`delegationId` 在步骤启动时就写进 journal**(`onDelegationStarted`
   回调从 `executeDelegateStep` 冒泡回调度层)。原先只在结算时记——**想看流的那一刻
   恰好没有 id**,正是最需要它的时刻。运行中的节点现在从第一秒起就可点开面板。
2. **桌面端:点节点按「有没有委派」分流**——有委派(delegate/synthesize)开
   「子智能体」面板看实时输出;门与复核没有流(前者一条命令、后者只有票决),
   仍开内联抽屉看命令与判定。节点 tooltip 写明「点了会开什么」。

### 7.10 复核(N 个评审)也要能看过程

7.9 把 delegate/synthesize 接上了活动流,复核被留了个口子(「只有票决」)。实机
反馈点着复核节点问「这个」。复核恰恰是最该看过程的:对抗式投票的价值在评审**各自
的检索与推理**,只看最后几行票决等于把过程丢了。补法:

- **sidecar**:`executeVerify` 的每个评审登记一条委派(`[workflow] 复核 i/N · <title>`,
  各自 `onActivity → pushActivity`、各自 `settleDelegation`),journal 里记
  `delegationIds`(顺序 = 评审 1..N);`onDelegationStarted` 改成 `onDelegationsStarted`
  并一次带上全部 id。
- **点击规则收敛成一条**:**一个委派 → 直接开面板看流**(delegate/synthesize);
  **0 个或 ≥2 个 → 开抽屉**(门:命令与判定;复核:票决 + 逐评审入口)。二选一不如
  把选择摆出来,抽屉里给每个评审一个「查看评审 i 的过程」按钮。

### 7.11 确认面改成审批卡形态 + 工作流卡脱离「过程面」折叠

两条实机反馈一次落地:

1. **确认面 = 审批卡**(「类似于审批那种方式,工作流放到上面,底部点确认还是驳回」)。
   composer 区的 ToolApprovalCard 是本应用「人要做决定」的标准形态,确认面板与它
   同族、同位置。原先那套「一行状态条 + 320px 弹层」的问题在图:弹层装不下编排图,
   图只能在里面横向滚。现在待确认状态下整条常驻条**升级成审批卡**——头行是标题与
   状态,主体是编排图(限高 300px 内滚,不把输入框顶出屏幕)+ 逐字命令门 + 参数槽,
   底部一行 驳回 / 确认并开始。弹层退休。
2. **工作流卡归「回答面」**(「不要放到大折叠内部,放出来」)。对话里工具行默认归
   过程面(`AssistantMessageVariant` 的 process),轮次折叠后就被收进「过程」里——
   而剧本卡/运行卡是**这一轮的交付面**(用户批准的剧本、运行结果),不是过程噪音。
   修法与 Task / generate_image 同款:`groupBy` 返回 `[]` 独立成行,`onAnswerSide`
   加上工作流两条工具名(与产物卡、检查点同一判断)。

### 7.12 完成态的常驻条不显示

「已完成 9/9 步 · 1.6M token ✕」这条对用户没有任何可做的事:报告已回投对话、
执行凭据在运行卡上,信息也已在那里(实机反馈:不要显示)。

规则收敛为一句:**常驻条只显示还需要你处理/还在跑的状态**——proposing / proposed /
running / paused / failed 显示,complete 隐藏。

连带问题必须一起解决:**清除入口原本只在这条上**,而槽位不清,下一条消息起不了新运行
(syncWorkflowOnUserPrompt 对非空槽不动)。所以清除按钮挪到运行卡的终止态头部
(「从工作流槽里清除这次运行(对话里的记录保留)」),点过即隐;sidecar 侧注释同步。

### 7.13 工作流面板(右侧 panel):整列宽度看编排图,并就地控制

「panel 侧可以查看工作流然后暂停,等等」。常驻条只有一行状态、对话卡与消息同宽,
编排图在两者里都是将就着看。面板是本应用「看一个正在跑的东西的细节」的既定位置
(子智能体面板同族),工作流也该有一个:

- **标签类型 `workflow`**(进「+」菜单与空态网格;不像 git 那样有档位前提——
  工作流档之外也可能有活着的运行)。视图 `agent-thread/agent-panel/workflow-tab.tsx`:
  头部一行是标题/状态读数/token 与**暂停·继续·清除**,主体是完整编排图;
  待确认时主体直接是 `WorkflowConfirmPanel`(填参数、确认/驳回都能在面板里做完)。
  点节点开详情沿用对话卡那条规则(一个委派 → 子智能体面板;0 或 ≥2 → 就地抽屉)。
- **入口三处**:运行卡头部的 ↗ 图标、常驻条标题(点标题即开)、「+」菜单。
- 数据源与常驻条、对话卡**同一个 pi-workflow store**:push 通知行为主通道、
  挂载水合一次、运行中 10s 低频对账——三处永远不会各说各话。

### 7.14 常驻条的空态也去掉

「描述要编排的任务,我先拟一份多智能体剧本…」这条虚线教程行没必要:建运行的入口
就是「在工作流档里发一条消息」,提案一到对话里就长出剧本卡(实机反馈:对话已经会
显示工作流了)。

守卫因此收成两句:没有运行不渲染、已完成不渲染——**常驻条只在「有活着的运行且还
需要你留意」时出现**:proposing / proposed / running / paused / failed。

### 7.15 线程键漂移:活槽必须按会话认亲,不能在别的键上恢复副本

最后一环,也是「刚编排就这样」的真因。转录把时间线钉死了:

```
18:02:56 running ×7   ← 确认 + 5 个调研步骤派发,执行器在跑
18:03:06 paused       ← 整整 10 秒后(轮询间隔)被恢复成一份暂停副本
```
而 run 文件里 5 个步骤都在跑。原因是**线程键漂移**:本会话新建的线程用草稿 id
(`__LOCALID_*`),页面刷新/热更新后变成会话 UUID。槽位按线程键存 —— 漂移后请求带着
新键来查,那个键上没有槽,于是 `restoreWorkflow` 从转录恢复出一份**副本**:一份在跑
(旧键,挂着执行器)、一份暂停(新键),UI 显示哪个全看谁最后写。7.8 的「活槽不可覆盖」
守卫只护住了**同一个键**,护不住换键。

修法:**按会话认亲**。`WorkflowRun` 记 `sessionId`(随对象迁移,不旁挂映射);
`adoptWorkflowSlot(threadId, sessionId)` 发现同会话的活槽挂在别的键下时,把它迁到
请求键并补推快照(migrateWorkflow 内做),而不是从磁盘恢复——磁盘那份永远比活槽旧。
`restoreWorkflow` 先认亲再考虑恢复;`get_workflow_state` / `workflow_step_detail` /
`confirm` / `resume` / `pause` / `clear` 六个入口一律先过一遍(幂等):
动作必须落到真正在跑的那个槽上,否则「继续」会拉起第二个执行器、清除清掉的是副本。

### 7.16 恢复写回的行丢了 cwd → 每恢复一次掉一层结果

7.15 修掉换键之后暴露出来的相邻缺陷:`restoreWorkflow` 自己写回那一行时用的是
`slimRunForTranscript(settled)` —— **不带 cwd**。而 cwd 是下次恢复找到
`.kova/workflows/<runId>.json`(结果与指纹的权威副本)的唯一线索。丢一次,
下一次恢复就退回瘦身行:结果全丢、已完成步骤重跑,UI 如实打上「历史步骤结果未能
读回」(实机:每次恢复都在掉结果,看到的正是这句)。

修法:写回时把读到的 `row.cwd` 原样带回。回归测试锁住「恢复两次后仍找得到 run 文件」。

### 7.17 「没看到有跑,线条都是灰」——运行态必须看得见

实机反馈:运行中的图上感知不到「在跑」。两个原因都在我这:

1. **连线只在来源是 done 时上色** —— 来源是 running 的边仍是灰的,于是整张图看着
   全是灰线;而灰线在直觉里就是「没动静」。
2. **运行中与已完成的视觉差太小** —— 两者都是绿框 + 绿点,只差描边深浅,6px 的
   脉冲点在静态视野里根本看不出在动。

改法(桌面端,热更即生效):
- **来源是 running 的边:翠绿虚线 + 流动动画**(`wf-edge-flow`,stroke-dashoffset
  循环)——静态图里唯一会动的东西,一眼看出「有东西正经过这条边」;来源 done 用
  实线翠绿(流已通过),failed 红,其余灰。
- **节点直接写状态词**:运行中 / 完成 / 失败 / 已中断 / 跳过(待跑不写)——不再要求
  用户从颜色深浅反推。
- **完成态的状态灯收敛为暗绿**,亮绿+脉冲从此专指「在跑」,不再两义。

### 7.18 「运行中的节点点不开面板」——一处回调漏传

实机观察被用户说得最准:**运行中的节点点不开面板,等它跑完再点就有了**。原因正是
7.9 那处「步骤启动时就写 delegationId」的接线漏了一环:`executeStepWithRetries` 的
重试循环调 `executeStepAttempt(...)` 时没把 `onDelegationsStarted` 传下去,于是那次
改动**从未真正生效**——delegationId 仍只在结算时写入(结算路径另一处),运行中的
步骤手里没有委派 id,UI 的点击规则(一个委派→面板;零个→抽屉)自然送错地方。

修法:补上透传;并加两条**结构断言测试**(重试循环必须透传该回调、步骤启动必须清
`endedAt`)——这类「接线断了一根线、行为静默降级」的问题单测覆盖不到执行链,
用结构断言兜底是该仓已有的做法(结构断言识别点同款)。

顺带:步骤(重)启动时清掉上一次尝试的 `endedAt`/`error`。不清的话 UI 用
`endedAt ?? now` 算时长会得到 0s/负数(实机:重试中的步骤显示「已 0s」)。

### 7.19 面板的「派活说明」（未能取得任务说明）

面板打开后第一条气泡是「任务说明」,来源一直是**主会话里那条 Task 工具行的 args.task**
(按 binding 的 toolCallId 命中,或按结果文本里的 "Delegation <8位> started" 认领)。
工作流的 delegate/verify 委派**没有 Task 工具行**,于是只能落到占位文案
「(未能取得任务说明)」——面板看得见过程,却不知道这一步被交代了什么。

修法:**让简报随委派一起走**。`DelegationRecord` 加 `task`(插值后的最终 prompt /
评审简报),创建处三处都写(Task 工具、工作流 delegate、工作流 verify);活动文件
meta 落盘时截断存 4k(重启回放仍可见);快照 RPC 回传;桌面 store 收进
`SubagentRunState.task`;面板取说明改为 **工具行优先,记录自带的 task 兜底**。

### 7.20 verify 的评审 id 报晚了(运行中的复核点不开面板)

7.19 之后暴露的姊妹问题:`executeVerify` 把 `onDelegationsStarted?.(reviewerIds)`
放在了 **`await Promise.all(...)` 之后** —— 也就是要等两位评审**都跑完** journal 才拿到
id。运行中的复核节点因此仍然没有 id,点开没有实时输出(delegate 路径没这个问题:
它在 `registerDelegation` 之后立刻报)。

修法:先建 promise 再 await(`Array.from` 的映射体是同步执行的,建的那一刻 N 位评审
已全部登记),在 await **之前**报出 id。结构断言锁住顺序。

### 7.21 线段从节点身上透出来

实机反馈「线段不要穿透」。原因是节点底色用了**半透明**写法
(`bg-emerald-500/[0.04]` / `bg-red-500/[0.07]` 这类),压在节点下方的 SVG 连线与箭头
就透出来了,被压住的邻列节点也露边。改为**不透明的 50/950 档**
(`bg-emerald-50 dark:bg-emerald-950` 等):连线仍从节点背后过(n8n/Dify 同款画法),
但不再透出;浅色与深色各自截图验收过。

### 7.22 交付注入漏成用户气泡（「跑完之后变这样了」）

运行结束时的交付注入（`[[workflow-continue]] … <workflow_report>…`，user 角色落转录）
**整段以用户消息直出**——模型指令、英文说明、原始报告包装全在气泡里。

两处投影都漏了这个前缀（契约层 `WORKFLOW_CONTINUE_PREFIX` 早就定义了「UI 各路径按
前缀隐藏」）：

- **sidecar 转录回放**（`transcript.ts` 的 `historyToUiMessages` 用户行分支）：只滤了
  auto-continue 与 goal 两族，补 `isWorkflowContinueText(up.text)`；
- **桌面直播投影**（`messageProjection.ts`）：只滤了 auto-continue，goal 与 workflow
  两族都漏，一并补上。

顺手在 pi-protocol 补了消息形状判定 `isWorkflowContinueMessage`（与
`isAutoContinueMessage` / `isGoalInternalMessage` 同款），两个投影共用——形态判定
与文本判定的差别（content 可能是数组）不再各写一遍。

### 7.23 只把「卡片」提到回答面,被驳回的提案尝试归回大折叠

7.11 把**所有**工作流工具行提到回答面,副作用在一次被驳回多次的提案上炸开:
对话里堆出八行「工作流剧本」(每次 rejected 尝试一行)——实机反馈
「其他放到大折叠,只保留工作流的那个图」。

判据落成一条纯函数(`lib/pi/workflow-part.ts` 的 `isWorkflowCardPart`):
**结果里有 `Run ID:` = 变成了卡片**(成功提案/按名跑剧本的回执都带它;被驳回的
尝试只回 rejected 文案)。据此:

- `groupBy`:卡片独立成行;尝试归 `group-tool`(与普通工具行同组);
- `onAnswerSide`:只有卡片;尝试留在过程面。

判据抽到独立模块是为了可测(5 条用例:成功/按名跑/rejected/错误信封/别的工具行),
assistant-message 只做投影。

### 7.24 「卡住了」的两个真因:认亲 flapping + 气泡测量的更新风暴

**① 认亲 flapping(我 7.15 引入的)。** `adoptWorkflowSlot` 是「把槽搬到请求键下」,
而两个调用方各用各的键(草稿 id / 会话 UUID),于是每 3-7 秒互相把槽拽回去一次,
每次还推一份快照。日志留下铁证(同一 run 在两个键之间来回 adopted)。
修法:**只查找、不搬运** —— `findWorkflowRun(threadId, sessionId)` 先按线程键、
再按 sessionId 回落;槽的写入键只有 `commitWorkflow(run, …)` 一处(run.threadId,
每 run 一个稳定键)。六个入口与两个载荷函数全部改为会话感知查找。

**② 子代理面板气泡的测量 effect 依赖 `children`。** `children` 每次渲染都是新
React 元素 → **每个流式增量都重建 ResizeObserver + setState**;工作流并发推流时
(每个 delegate/评审都是一条活动流)打成「Maximum update depth exceeded」,页面冻住。
修法:依赖改空(挂载一次,内容变化由 observer 驱动)+ measure 只在值真变时写 +
rAF 合并 observer 回调。
