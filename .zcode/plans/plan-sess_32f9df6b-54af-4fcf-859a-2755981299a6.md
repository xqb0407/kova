## 关键发现（决定整个设计的两点）

**1. 执行点只有一个。** `bash` 在 Rust 侧由 [tool_exec.rs:253](/Users/herther/Desktop/ai-teamplte/apps/desktop/src-tauri/src/tool_exec.rs:253) 的 `run_bash` 和后台版 `run_bash_background` 各自建 `Command`，两者都走同一个 `resolve_shell_command()`。套沙箱就是在 argv 前面插一层包装 —— **两个调用点、一个 helper**，不需要动别处。

**2. sidecar 已经在每个工具调用的信封里给了 Rust 全部上下文**（`{ name, cwd, params, owner, secretEnv }`）。规则**不需要**在 Rust 再读一遍文件：sidecar 是规则的唯一所有者，把「这次可写哪些根」算好放进信封，Rust 只负责执行。这样规则可单测、可调试，也不会出现两份配置。

## 第一步：可写根清单（小、独立可用）

**它自己就有价值**：解决你说的「跨项目也是」—— 在 `write`/`edit` 的审批里认一份清单，配过一次的目录之后不再问。

**配置文件三层**（形状与优先级都抄 Claude Code 那套）：

```
~/.kova/permissions.json          用户级：所有项目
<cwd>/.kova/permissions.json      项目共享：进 git，团队同一份
<cwd>/.kova/permissions.local.json 项目本地：本机、自动加 .git/info/exclude
```

```json
{ "writeRoots": ["../shared-lib", "~/work/cache"] }
```

相对路径相对 cwd 解析，支持 `~`；越大范围优先级越高（local > project > user）。

**安全规则：项目文件只能收紧，不能放宽。** 这是我查 Claude Code 时挖到的最值得抄的一条 —— `permissions.defaultMode` 里的 `auto`/`bypassPermissions` 从项目/本地文件里**根本不生效**，只有用户级和企业级能设；`allow` 规则也要等「工作区信任」。理由很实际：**clone 别人的仓库不该让那个仓库给自己授权**。

落到这里就是：**`.kova/permissions.json` 里新声明的 `writeRoots` 不算数，直到你在本机信任过这个工作区**。信任是一个新的小机制（按工作区路径记进 kv），首次遇到项目文件里的 writeRoots 时弹一次「这个项目想放行额外可写目录：…」，你点头之后才生效。本地级和用户级不受这条限制（那是你自己写的）。

改动面：sidecar 新模块 `permissions/write-roots.ts`（纯函数：加载/合并/解析 + 单测）+ `modeBeforeToolCall` 里 `workspace-write` 分支认它 + 一次性的信任询问（走现成的 `question` 通道，不新造交互）。

## 第二步：bash 沙箱（大）

**机制**：macOS `sandbox-exec`（seatbelt，Codex 同款），profile 形如：

```
(version 1)
(allow default)                    ; 读放开、网络放开
(deny file-write*)                 ; 写全部拒绝
(allow file-write*
  (subpath "<工作区>")              ; 工作区
  (subpath "/private/tmp"))        ; 系统临时目录（/tmp 是指向它的软链）
(allow file-write-data (literal "/dev/null"))
```

**默认可写集只有两条**：工作区 + 系统临时目录。不预先枚举 `~/.npm`、`~/.cargo` 那些 —— 那正是上一轮说清楚的「列不完、且列错了会误伤正常命令」的坑。

**边界如实声明**：v1 只支持 macOS。Linux 要 bubblewrap/landlock、Windows 要 AppContainer，都不在这一次；其他平台**不套沙箱**（= 今天的行为，不倒退），档位说明里写清。

**把「平台 → 沙箱后端」做成一个可替换的函数**。`sandbox-exec` 自 10.15 起被 Apple 标记弃用（仍可用，Codex 也在用）；哪天它真被拿掉，只改那一个函数。

**生效范围**：只包 bash（含后台 bash）。**`write`/`edit` 不套** —— 那两个的授权已经由审批给过了，再加一道内核拦截会出现「你明明点了同意但写不进去」。

## 第三步：拒绝之后要能升级为一次审批（不做这个，第二步就是负优化）

沙箱上线后第一种体验必然是：`npm install` 被拦、`git push` 被拦、python 写缓存被拦 —— 因为可写集只有工作区和临时目录。**如果只是让命令失败**，模型会以为是自己命令写错了、换个写法再试，用户看到的是一堆莫名其妙的 EPERM。

所以闭环是：**沙箱拒绝 → 认出这是沙箱拒绝（stderr 里有 sandbox deny 信息）→ 把「这条命令想写 X」翻译成一次审批 → 你同意 → 同一条命令在沙箱外重跑一次。**

配套两处：

- 确认卡加第三个按钮「允许并记住」，`tool_confirm` 带 `remember: "project" | "user"`，sidecar 把那个目录写进对应的 permissions 文件（这就是清单「从失败中长出来」的落点）；
- 这是**第二步必须先于上线的前置**，不是可选的收尾项。

## 验证

- **Rust**（macOS）：沙箱内 `echo x > 工作区/文件` 成功；`echo x > /tmp/文件` 成功；`echo x > ../同级目录/文件` 失败；`echo x > ~/文件` 失败。四个方向各一条，跑在 `cargo test` 里。
- **sidecar 纯函数**：三层合并优先级、相对路径与 `~` 展开、项目文件未信任时不生效、`deny` 优先。
- **端到端手测**：`工作区内自动` 档让 agent `echo x > ../out.txt` → 被拦 → 弹审批 → 同意并记住 → 重跑成功 → 第二次不再问。

## 明确不做

- **网络限制**：`(deny network*)` 会把 npm / git fetch / 任何要联网的脚本全废掉。留作后续开关，不在这两歩里。
- **Linux / Windows 沙箱**：机制完全不同，各自是独立一轮。
- **给 `write`/`edit` 加内核拦截**：理由见上。
- **预先枚举工具链缓存目录**：理由见上一轮（列不完、误伤代价高于多问一句）。

## 建议的推进顺序

**先只做第一步**。它小而完整、单独可用（跨项目改文件不再每次问），而且它是第二步的地基 —— 清单文件、三层优先级、信任机制、审批卡那个「允许并记住」按钮，第二步全都要用。做完第一步实际用一阵子，看清单会长成什么样，再决定沙箱的可写集要不要跟着调整。
