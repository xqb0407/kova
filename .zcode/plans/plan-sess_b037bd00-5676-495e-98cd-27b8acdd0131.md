# 项目 · 数字员工工作台

## 你要的七件事，拆成四个里程碑

1. 用户新建项目
2. 项目里邀请专家子智能体
3. 项目输出文件
4. 主 agent 发布任务
5. 子 agent 自行领取任务
6. 任务看板
7. 项目可加技能/MCP
8. 群聊沟通

**M1 项目骨架与成员名单**（1、2、3 的壳）
**M2 任务看板与自行领取**（4、5、6）
**M3 群聊**（8）
**M4 技能/MCP 挂载与产出归档**（7、3 的实体）

按这个顺序是因为 M1+M2 就能独立产生价值，M3 是风险最高的一块（见下），放第三个可以先拿到可用的东西再冒险。

## 四个架构决定（你没选，我按推荐项定，改动成本低）

**决定一：项目 = 用户指定的一个文件夹**（推荐项，未选）
项目的配置、看板、群聊都落在 `<目录>/.kova/project/` 下。
*为什么：* 技能和 MCP 已经是按工作目录隔离的，选目录型项目等于白捡这两块。成员直接读写项目目录，"项目输出文件"天然就是这个目录里的东西，不需要再做一套产出管理。
*代价：* 用户得先有或新建一个文件夹。

**决定二：群聊用事件驱动唤醒，不用常驻循环**（推荐项，未选）
群里有人发言或发布任务时，sidecar 才唤醒相关成员各跑一个回合；没人说话时完全不烧 token。
*为什么：* 常驻自主循环看着最像真实团队，但它持续烧 token、难停止、容易空转烧钱，而且没法向用户解释"它为什么突然说话"。

**决定三：领取由成员自己决定，系统只做原子占位**（推荐项，未选）
有任务发布时唤醒全体受邀成员，成员在自己的回合里看到待领列表，用 `claim_task` 自己决定要不要领。系统不替成员做能力匹配。
*为什么：* 你要的正是"自行领取"。规则式自动派活猜错时没人兜底。

**决定四：项目的技能/MCP 是"在全局基础上加装"，不是白名单限制**（推荐项，未选）
成员在项目里可用 = 全局启用的 + 项目显式添加的。
*为什么：* 限制语义更干净，但每个项目都要重复配置一遍全局已有的东西，上手很重。

## 数据模型

**项目注册表**用现有 kv（`kvGet`/`kvSet`，生产走 Rust host RPC、测试走本地 sqlite，两边同一套代码）单键存 JSON 数组。这样项目列表视图能查，又不需要索引一致性维护。

**项目本地文件**在 `<cwd>/.kova/project/`：

- `chat.jsonl` — 群聊记录，只追加。沿用 `team/board.ts` 的 JSONL 护栏（超 5MB 重写为仅保留末尾 1MB）。
- `tasks.json` — **单个 JSON 文档，不是 JSONL**。这是刻意的区别：任务状态是可变的（待领取→领取中→完成），而任务板是纯追加的台账。领取的原子性靠"同步读-改-写"实现——`readFileSync`/`writeFileSync` 在单线程 JS 里天然不会被另一个领取插进来，不需要引入事务。
- `members.json` — 受邀成员名单（存的是子智能体名，指向既有三层定义，不复制定义本体）。

**为什么项目不新增子智能体实体**：项目邀请的是**已有的**子智能体定义（内置/系统/工作区），项目只存名字。定义改了项目里跟着改，不会有两份事实源。

## M2：任务看板与自行领取

**sidecar**
- `src/project/store.ts` 扩展 — 任务记录 `{id, title, detail, status, createdBy, claimedBy, claimedAt, completedAt, result, artifacts[]}`；`claimTask` / `listTasks` / `updateTask`。`claimTask` 校验 `status === "open"`，否则报"已被 X 领走"。
- `src/project/scheduler.ts`（新）— 唤醒队列。复用 `automation/runner.ts` 里已导出的 `SubagentRun` + `buildMemberTools` + `resolveMemberModel`。带**扇出预算**：一条用户消息最多触发 N 次成员运行（默认 8），防止成员互相 @ 无限对喷烧钱。
- `src/project/tools.ts`（新）— 成员侧工具 `speak` / `list_tasks` / `claim_task` / `submit_task`；主代理侧工具 `project_publish_task`。
- 主代理侧工具按 `buildAgentExtensions`（`sessions/resolve.ts:79`）的既有模式挂载。

**重启时的孤儿任务**：sidecar 重启后处于"领取中"但没有活运行的任务，回收为"待领取"并在群里留一句说明。**不伪造完成**——沿用 `team/board.ts` 里已经写明的原则：丢掉一个正在跑的事实可以，编造一行 completed 是撒谎。

**desktop**
- `components/projects/project-board.tsx`（新）— 四列看板：待领取 / 进行中 / 已完成 / 失败。**先不做拖拽**，用按钮改状态（现有 UI 原语够用，`components/ui/` 里没有拖拽组件，硬上会引依赖）。

## M3：群聊（风险最高，放第三个）

这是唯一需要**新增 agent 间通信原语**的里程碑。现状是子代理之间完全不能说话。

- `chat.jsonl` 消息 `{id, seq, author: "user"|"main"|"member", text, ts, mentions[]}`。
- 唤醒规则：新消息进来 → 算唤醒集（@ 到的成员 + 发任务时全体受邀成员）→ 各跑一个回合。
- 成员的报告**不进任何人的上下文**（避免上下文污染，和现在 Task 报告的处理一致）。
- 扇出预算同样在这里生效。

**风险说清楚**：这是真正在扩展 agent 运行时模型，不是在既有管线上加功能。模型有概率不按预期调用工具、或对着消息空转一轮。我会在这一里程碑单独停下来让你验收，不要指望它一次过。

## M4：技能/MCP 挂载与产出归档

- `project.skills` / `project.mcpServers` 叠加到成员的工具装配上（改 `buildMemberTools` 的调用方，成员定义的白名单优先级高于项目加装）。
- 成员 `submit_task` 时可带 `artifacts[]`（相对项目目录的路径），产出文件在项目详情页分组展示，可直接打开。
- MCP 需要单独确认：现在的 MCP 工具是全局连接池，项目级挂载意味着要按项目过滤可见工具，这块我需要再核一遍连接池的实现细节再动手。
