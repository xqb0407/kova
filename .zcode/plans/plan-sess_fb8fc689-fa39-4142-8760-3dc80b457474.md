## 目标

给这个 Tauri 桌面应用（`output: "export"` 静态导出 + 193 个 tsx 挂在单一 `page.tsx` 下）补上分层错误边界，把「一处 render 抛错 → 整个窗口白屏 → 只能杀进程重开」降级为「某个区域显示崩溃提示 → 切走再切回或点重试即恢复」。

## 关键约束（已核实）

- `next@16.3.4`：`error.tsx` 的 `retry` prop 自 v16.3.0 起 stable，不用 `unstable_retry`。
- `next.config.ts` 是 `output: "export"`。`app/error.tsx` 在根 layout 之内渲染，**能**用到 `globals.css`；`app/global-error.tsx` 替换根 layout，按官方文档**不包含**全局样式，只能自带样式。
- `installFrontendLogging()` 装在 `AppRuntimeProvider` 的 `useEffect` 里（`app-runtime-provider.tsx:274`）。**接了边界之后这条链就断了**：React 捕获到错误后只调 `componentDidCatch`，不再抛到 `window`，`frontend-logging.ts:61` 那个 `error` 监听再也收不到。所以必须让边界主动落盘。
- `about::open_logs_dir` 已在 `lib.rs:131` 注册，直接用，不用改 Rust。
- `TabContentView` 已经以 `key={tab.id}` 挂载（`agent-panel/index.tsx:267`），切 tab 即重挂载 —— 边界跟着 key 走就自动获得「切走再切回」的恢复能力。
- 无 `react-error-boundary` 依赖，手写 class 组件（~50 行），不引新包。
- 桌面端没有 test script，验证靠 `bun run build`（含静态导出）+ tsc。

## 改动清单

### 1. `apps/desktop/lib/frontend-logging.ts` — 导出主动上报

在现有 `send()` 旁新增导出：

```ts
/** 边界接住的错误不会再冒泡到 window，必须由调用方显式落盘 */
export function reportFrontendError(message: string): void {
  if (!isTauri()) { console.error(message); return; }
  send("error", message);
}
```

`send` / `formatArgs` 已是模块私有的，直接复用，不动现有逻辑。

### 2. `apps/desktop/components/ui/error-boundary.tsx` — 新建

`"use client"`，class 组件（对齐 Next 文档里 `GracefullyDegradingErrorBoundary` 的形态）：

- `state: { error: Error | null }`
- `static getDerivedStateFromError` 置位
- `componentDidCatch(error, errorInfo)` 调 `reportFrontendError()`，内容为 `label` + `error.message` + 前几帧 stack + `componentStack`（复用 `frontend-logging` 的 stack 截断思路）
- props：`{ children, label, fallback? }`。**不提供 `resetKey`** —— 恢复一律靠调用点的 `key` 重挂载（和现有 `key={tab.id}` 同一套 idiom），少一个 API 少一处出错可能
- 崩溃态渲染 `fallback ?? <PanelCrash label={label} onRetry={...} />`

同文件导出 `PanelCrash`：面板内的紧凑崩溃态，视觉沿用 `tab-empty.tsx` 的 `text-muted-foreground/60` + `flex h-full flex-col items-center justify-center` 那一套，三个动作：

- **重试** — `setState({ error: null })` 重渲子树
- **复制错误** — `navigator.clipboard.writeText`（和 `git-graph.tsx:148`、`input-copy.tsx:88` 同款，远程端也能用）
- **打开日志目录** — `invoke("open_logs_dir")`，仅 `isTauri()` 时渲染该按钮

按钮用现成的 `ui/button`（`variant="outline"` / `destructive`，`size="sm"`），图标用 lucide。

### 3. `apps/desktop/app/error.tsx` — 新建（整棵树的兜底）

`"use client"`，default export 接 `{ error, retry }`。它渲染在根 layout 内部，`globals.css` 生效，可以直接用 Tailwind token（`--destructive` / `--muted-foreground` 都有）。布局用 `flex h-dvh flex-col items-center justify-center`，复用 `PanelCrash` 的主体但换成全屏版式，带 `<title>` 和「重新加载」按钮（`retry()` 失败时用户还有 `location.reload()` 兜底，所以两个都给）。

### 4. `apps/desktop/app/global-error.tsx` — 新建（最后一道）

`"use client"`，同样接 `{ error, retry }`，**自带 `<html><body>`**。因为拿不到 `globals.css`，不引外部 CSS 文件、不用 Tailwind class，改为组件内一个 `<style>` 标签写最小样式，颜色用 `prefers-color-scheme` 媒体查询兜住明暗（根 layout 的 `UI_PREFS_BOOTSTRAP` 在这个路径下不执行，`html.dark` 不会带上，所以不能依赖 class）。内容：错误文案 + 「重试」+「重新加载」+「复制错误」。不导 `metadata`（文档明确不支持）。

### 5. `apps/desktop/components/agent-thread/base.tsx` — 主区边界

第 715-716 行 `<div className="relative z-10 flex-1 overflow-hidden">{chat}</div>`，把 `{chat}` 包起来，key 用 `activeMenu`：

```tsx
<ErrorBoundary key={activeMenu} label="主区">
  {chat}
</ErrorBoundary>
```

`chat` 那一坨是 `activeMenu` 的三元链（Thread / FilesView / MarketplaceView / AutomationsView / UsageStatsView），切菜单天然重挂载 → FilesView 崩了切到设置再切回来就恢复。

同文件第 927 行的 `{view === "settings" && ...}` 是 `fixed inset-0 z-50` 的全窗口覆盖，同样包一层 `key={view}`，否则设置页崩了会留下一个坏死的遮罩。

### 6. `apps/desktop/components/agent-thread/agent-panel/index.tsx` — 面板 tab 边界

第 267 行把 `key` 从 `TabContentView` 挪到边界上（语义不变：仍是「以 tab.id 重挂载」，只是重挂载的根变成了边界）：

```tsx
<ErrorBoundary key={active.id} label={`面板标签 ${tabTitle(active)}`}>
  <TabContentView tab={active} />
</ErrorBoundary>
```

`ShellTab` / `BrowserView` / `PluginPanelHost`（iframe + srcdoc）这些高风险子树崩了，只会坏掉那一个标签页，其余标签和整个应用照常用。

## 不做的事

- 不加 `app/error.tsx` 之外的 route 级 `error.tsx`（生产只有一条路由，`dev-preview/*` 不对外）。
- 不动 `frontend_log` 的 Rust 实现，不加新的 Tauri command。
- 不引 `react-error-boundary` 依赖。
- 不碰 assistant-ui / streamdown 内部。

## 验证

1. `cd apps/desktop && bunx tsc --noEmit` —— 三个新 tsx 的类型（`strict: true`）。
2. `bun run build` —— 确认 `output: "export"` 下三个新文件都能进 `out/`，静态导出不被破坏。这是本次唯一有实际失败风险的步骤，导出报错要先修完再收工。
3. 人工验证（需要起 Tauri，我会说明怎么触发）：临时在某个 tab 视图里 `throw new Error("boom")`，确认崩的是那一个标签、点重试能恢复；再在 `Base` 顶层 throw 一次确认走到 `app/error.tsx` 而非白屏。**这步需要你决定要不要我在实现里留一个临时的触发开关**（默认不留，改完即删）。

## 风险

- 边界接住错误后，React 不再把它抛到 `window`，`frontend-logging.ts:61` 的 `error` 监听对**渲染期错误**会失效（`unhandledrejection` 和事件回调里的错误不受影响）。这是加边界的必然代价，由第 1 步的 `reportFrontendError` 补上；非渲染期的错误仍然照旧进 `web.log`。
- `global-error.tsx` 在这条代码路径上几乎不会被触发（根 layout 只有 html/body/Toaster），它的价值是「`app/error.tsx` 自己抛错」时的兜底。成本 30 行，留着。
