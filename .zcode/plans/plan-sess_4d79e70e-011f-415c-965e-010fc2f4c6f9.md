## 实现方案：provider 自动重试 + UI 重试卡片

**核心前提**：sidecar 的 `@earendil-works/pi-ai` / `pi-agent-core` 均为 **0.85.1**，与 PI-Desktop-main 完全同版本，其 `provider-retry.ts` / `agent-errors.ts` 可近乎原样移植。范围按已确认的选择：**只重试流建立前的失败**（429/5xx/网络错误/超时），流中断与预算耗尽仍走现有报错路径（手动 Retry = 操作栏已有的 Reload）。

### Sidecar（3 个新文件 + 3 处接线）

1. **`sidecar/pi-agent/src/agent-errors.ts`（新）** — 移植错误分类器 `classifyAgentError`：从错误对象/message 提取 HTTP status、按关键字分类为 `NETWORK_ERROR / TIMEOUT / STREAM_FAILED / PROVIDER_ERROR / PROVIDER_RATE_LIMITED / PROVIDER_UNAUTHORIZED / CONTEXT_TOO_LARGE / TURN_ABORTED` 并给出 `retriable`；含敏感信息脱敏与长度截断。

2. **`sidecar/pi-agent/src/provider-retry.ts`（新）** — 移植重试引擎（去掉 `@pi-desktop/shared` 依赖，常量内联）：
   - 预算：最多 10 次；429 走指数退避 2s 基数 +25% 抖动封顶 30s；其他瞬时错误 1→2→4→8s 封顶；`Retry-After` / `retry-after-ms` 响应头优先于本地退避。
   - `captureProviderResponse`：包 fetch 记录失败响应的 status/headers（pi-ai 的 onResponse 不暴露失败 429 的头）。
   - `createProviderRetryStream`：只吞流建立前（`!sawStart`）的错误事件并重试，`maxRetries: 0` 关掉 SDK 内置重试；含 opaque 400/422 的一次性 output-limit 修复。
   - **本项目特有的两个可选钩子**（参考项目没有，因 UI 通道不同）：`onRetry({attempt,maxRetries,delayMs,error})`、`onSettled()`——后者在流成功 start 或终态错误被转发时各触发一次（每轮重试周期只发一次），保证重试卡片不会残留倒计时。

3. **`sidecar/pi-agent/src/types.ts`** — `Running` 增加重试状态：`providerRateLimitRetryAttempt`、`providerTransientRetryAttempt`、`retryCapture { status?, headers? }`、`retryChunkId`（每轮 prompt 一个 data part id，同 id 原地更新）。新增 `createRetryController(run)` 放本文件旁边或 provider-retry.ts 内：claim 预算逻辑（429 独立预算；`NETWORK_ERROR/TIMEOUT/STREAM_FAILED/PROVIDER_ERROR` 共享预算；其余不重试）+ onRetry/onSettled 里用 `sendEventChunk` 发 `{type:"data-retry", id, data:{phase:"retrying"|"resolved", attempt, maxRetries, delayMs, code, error}}`（`run.stopRequested` 时静默）。

4. **`sidecar/pi-agent/src/sessions.ts:107`** — Agent 的 `streamFn` 包一层：重置 capture → `maxRetries: 0` + `fetch: captureProviderResponse(...)` → `createProviderRetryStream(m, context, opts, (o)=>getModels().streamSimple(m,context,o), controller)`。退避 sleep 用 `options.signal`（已确认 pi-agent-core 会把 abort signal 传入），Stop 立即打断等待。

5. **`sidecar/pi-agent/src/protocol.ts`** — `dispatchPrompt` 开头（`run.stopRequested = false` 处）重置两个重试计数器与新 retryChunkId。

6. **`sidecar/pi-agent/src/subagent.ts:256`** — 委派子代理的 streamFn 同样包重试（预算挂在各自 run、静默只记 logErr，不占 UI 流）。

### 前端（2 个文件）

7. **`components/agent-thread/retry-card.tsx`（新）** — 样式照 `session-events.tsx` 的 Retry 组件：橙色卡（`border-orange-500/30 bg-orange-500/10 text-orange-600 dark:text-orange-400`）+ `RefreshCw animate-spin` + 「请求失败，正在重试 (attempt/maxRetries) · Ns 后重试」本地倒计时（attempt 变化即重置）。`phase:"resolved"` 返回 null（卡片原地消失）。用 `makeAssistantDataUI({ name: "retry" })` 注册——与 compaction 横幅同机制，`lib/pi-transport.ts` 的 transform 不拦截未知 data chunk，零改动直通。

8. **`components/agent-thread/thread.tsx:89`** — `<CompactionDataUI />` 旁挂 `<RetryDataUI />`。

### 测试与验证

- 移植 `provider-retry.test.ts`、`agent-errors.test.ts` 到 sidecar（改 import、常量本地化），补一条 controller 用例（claim 预算 + data-retry chunk 形状 + resolved 恰好一次）；`bun test` 全绿。
- 手动冒烟：在设置里加一个指向关闭端口的自定义 provider（ECONNREFUSED）→ 应看到卡片按 1/2/4/8s 走完 10 次尝试后出红色错误框 → 点 Reload 重新执行；Stop 应在倒计时中立即终止且卡片消失。
- 类型检查/lint 随项目现有脚本跑。

**不做**：流中断（start 之后失败）的自动续跑（需要弹掉失败 assistant 消息并 `agent.continue()`，涉及 JSONL 持久化残留，明确超出本次范围）；错误框内新按钮（沿用现有 Reload）。
